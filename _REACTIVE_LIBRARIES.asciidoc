= Reactive Libraries
:toc:
:toclevels: 2

A survey of the Java reactive ecosystem, with a focus on the libraries this project
interoperates with.
Entries note *primary types*, *use case*, *API surface* (which publisher contract —
`org.reactivestreams.Publisher` or `java.util.concurrent.Flow.Publisher`),
*TCK conformance* (whether the library passes the Reactive Streams TCK),
*prefetch behaviour* (how downstream `request(n)` is forwarded), and *status*.

'''

== Background: two equivalent API surfaces

The Reactive Streams 1.0 specification (2015) defines four interfaces under
`org.reactivestreams.*` — `Publisher`, `Subscriber`, `Subscription`, `Processor`.

JEP 266 (Java 9, 2017) promoted those interfaces into the JDK under
`java.util.concurrent.Flow.*` with *byte-for-byte identical method shapes*.
The two interface families are not type-compatible (different packages), but the
`reactive-streams-flow-adapters` library provides 1:1 zero-cost adapters
(`FlowAdapters.toFlowPublisher`, `FlowAdapters.toPublisher`, etc.) and most
implementations expose both surfaces or pick one and offer adapter classes.

Choose `Flow.*` when JDK-only is a hard requirement (no external dependency).
Choose `org.reactivestreams.*` when interop with the broader ecosystem matters — most
existing libraries pre-date JEP 266 and stayed on the `org.reactivestreams.*` API.

'''

== 3. Adapters and Bridges

Entries below are ordered by direct usage in this project's tests.

[%unbreakable%autowidth.stretch,frame="none",grid="rows"]
|===
| Library / Module | Bridge | Notes

| `reactive-streams-flow-adapters` (used ✓)
| org.reactivestreams.Publisher ↔ Flow.Publisher
| The canonical 1:1 adapter; zero-cost (no buffering).
Required to interoperate between sections 1 and 2.
Used in `HelloWorldFlow` and in every `_Mutiny_Test` / `_Helidon_Test` to bridge our
RS publisher into a `Flow.Publisher`.

| Mutiny `Multi.createFrom().publisher(...)` (used ✓)
| accepts both Flow.Publisher and org.reactivestreams.Publisher (via overloads)
| The conversion path through Multi introduces prefetch buffering — downstream
`request(n)` does *not* forward 1:1 upstream.
This is why our `_Mutiny_Test` set has no `__randomLessThan12` scenario.

| Akka/Pekko Streams `Source.fromPublisher(...)` / `Sink.asPublisher(...)` (used ✓)
| Source ↔ Publisher at the boundary
| Inside the stream, Akka/Pekko's own backpressure protocol replaces the Reactive Streams
demand protocol.
Used by the `_Akka_Test` set.

| Reactor `JdkFlowAdapter`
| Flux ↔ Flow.Publisher
| Reactor's first-class adapter to/from JDK Flow.
Not used by the `_Reactor_Test` set (we subscribe RS publishers directly via
`Flux.from(...)`).

| RxJava `FlowAdapters` _(planned)_
| Equivalent in development
| Currently use the `reactive-streams-flow-adapters` artifact externally.
|===

== 4. Choosing one — a brief guide

The pragmatic decision matrix:

* *Spring application?* → Project Reactor.
Already on the classpath via Spring WebFlux / Spring Data R2DBC.
* *Quarkus application?* → SmallRye Mutiny.
Quarkus extensions are written against Mutiny.
* *Android or RxJava-experienced team?* → RxJava 3.
* *JVM-only, no third-party RS dependency wanted?* → JDK `Flow` built-ins
(`SubmissionPublisher`), plus `reactive-streams-flow-adapters` if you need to interoperate.
* *Stream-graph DSL with distributed workers / actors?* → Apache Pekko Streams (preferred
over Akka for new projects due to licensing).
* *Just consuming a reactive driver (Mongo, R2DBC, Cassandra)?* → use whichever wrapper the
driver vendor publishes.
Most ship Reactor-flavoured wrappers.

The conformance gap to worry about is *prefetch*: every high-level adapter (Reactor's
`Flux.from(...)`, Mutiny's `Multi.createFrom().publisher(...)`, RxJava's
`Flowable.fromPublisher(...)`) may request more from your upstream than the downstream
asked for.
This is by-design for throughput, but it means an upstream publisher that strictly respects
1:1 demand cannot be tested through these adapters with single-item-at-a-time scenarios —
the adapter will pull in batches and signal completion eagerly.
Test such strict-demand behaviour with a raw `Subscriber` against `org.reactivestreams.*`
directly.

'''

== 5. Notes on what's _not_ listed

* *Vavr-Jackson*, *Reactor Kafka*, *Reactor RabbitMQ*, *akka-kafka* etc. — domain connectors
built on top of the section-1 libraries; they inherit their parent's TCK and prefetch
behaviour.
* *Spring Reactor Test* (`reactor-test`) — testing utilities, not a publisher implementation.
* *JDK `Flux` / `Mono`* — these do *not* exist in the JDK; they are Reactor types.
The JDK ships `SubmissionPublisher` only.
* *CompletableFuture / CompletionStage* — single-value asynchronous primitives.
Not part of Reactive Streams (no backpressure, no multi-value semantics), though
Mono / Uni / Single exist as 0/1-value reactive analogues with conversion methods.
