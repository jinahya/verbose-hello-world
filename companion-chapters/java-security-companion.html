java.security

java.security 는 자바 보안 프레임워크의 바탕이 되는 패키지이다.[1] 메시지 다이제스트, 전자 서명, 키와 키 쌍 생성, 보안 난수 생성 같은 연산을 맡는 엔진 클래스를 제공한다. 엔진 클래스의 인스턴스는 생성자 대신 알고리즘 이름을 받는 getInstance(…​) 로 얻는다. 요청한 알고리즘을 구현한 제공자 (provider) 가 없으면 getInstance(…​) 는 검사형 예외인 NoSuchAlgorithmException 을 던진다. 이 절에서는 MessageDigest, Signature, 그리고 SecureRandom 을 다룬다.

이 책은 Java 의 보안 (security) 과 암호 (cryptography) 자체를 다루는 책이 아니다. 이 절은 HelloWorld 의 세 메서드가 쓰는 타입만 최소한으로 소개한다. 키 관리, 알고리즘 선정 같은 실제 운영 환경의 고려 사항은 별도의 전문 자료를 참고하기 바란다.

java.security.MessageDigest

java.security.MessageDigest 클래스는 임의 길이의 바이트 입력으로부터 고정 길이의 해시 (digest) 를 산출하는 단방향 해시 함수의 추상화이다.[2] 같은 입력은 항상 같은 해시를 산출하지만, 해시로부터 원본을 복원하거나 같은 해시를 만드는 다른 입력을 찾는 것은 계산적으로 불가능하도록 설계되어 있다. 이 성질이 무결성 검증, 서명, 콘텐츠 식별 등 다양한 보안 용도의 토대가 된다.

java.security.MessageDigest
package java.security;

public abstract class MessageDigest extends MessageDigestSpi {

    public void update(byte[] input) { ... }

    ...
}

MessageDigest 인스턴스는 알고리즘 이름으로 얻는다 (MessageDigest.getInstance("SHA-256")). 일단 얻은 인스턴스는 상태를 가진 누적기처럼 동작한다. update(…​) 호출은 입력을 내부 상태에 반영하고, digest(…​) 호출은 그 시점까지 넣은 입력 전체에 대한 해시를 완성해 돌려주면서 내부 상태를 초기화한다.

void update(byte[] input)

배열 전체의 바이트를 누적한다. update(input, 0, input.length) 와 같다. 반환값이 없으며 (void), 누적은 부수 효과로만 일어난다. 같은 입력으로 두 번 갱신하면 그만큼 두 번 누적된다. HelloWorld#update(MessageDigest) 는 hello, world 의 12 바이트를 이 메서드에 한 번에 넘긴다.[3]

분할 입력의 동등성. update(a) 후 update(b) 를 호출한 결과는 a 와 b 를 이어 붙인 한 덩어리로 한 번에 update(…​) 를 호출하여 갱신한 결과와 비트 단위로 동일하다. 이 성질 덕분에 큰 파일 전체를 메모리에 올리지 않고 조각조각 갱신할 수 있다.

DigestOutputStream 과 DigestInputStream

java.security.DigestOutputStream 과 java.security.DigestInputStream 은 각각 출력 / 입력 스트림을 지나가는 바이트로 MessageDigest 를 함께 갱신하는 데코레이터 (decorator) 다.[4][5] 전자는 write(…​) 로 보낸 바이트가 하부 스트림에 도달하는 동시에 다이제스트에 누적되고, 후자는 read(…​) 로 받은 바이트가 호출자에게 돌아가는 동시에 다이제스트에 누적된다. 어느 쪽이든 호출자가 digest.update(…​) 를 직접 부를 필요가 없다.

HelloWorld#update(MessageDigest) 처럼 digest.update(byte[]) 를 한 번 직접 호출하는 것이 가장 짧은 경로라면, 이 두 스트림은 같은 바이트열을 입출력 과정에 통과시키면서 같은 결과를 얻는 다른 경로다. 같은 12 바이트가 같은 알고리즘을 거치는 한 결과는 동일하다.

DigestOutputStream / DigestInputStream 으로 같은 12 바이트가 같은 다이제스트를 만든다
try (var dos = new DigestOutputStream(OutputStream.nullOutputStream(),
                                      MessageDigest.getInstance(algorithm))) {    (1)
    service().write(dos).flush();                                                 (2)
    try (var dis = new DigestInputStream(hello_world_inputstream(),
                                         MessageDigest.getInstance(algorithm))) { (3)
        dis.transferTo(OutputStream.nullOutputStream());                          (4)
        assertArrayEquals(dos.getMessageDigest().digest(),
                          dis.getMessageDigest().digest());                       (5)
    }
}
1 출력 측 데코레이터를 만든다. 하부 싱크는 OutputStream.nullOutputStream() 이므로 실제 바이트는 버려지지만, 기록된 모든 바이트가 안쪽의 새 MessageDigest 에 누적된다. 데이터가 아니라 다이제스트가 목적인 셈이다.
2 service().write(dos) 가 12 바이트를 dos 에 보낸다. 이 예에서는 write(OutputStream) 을 hello, world 12 바이트를 쓰도록 스텁해 두었으므로, 독자가 구현한 메서드가 아니라 두 데코레이터의 동작을 보여 준다. 별도의 digest.update(…​) 호출이 필요 없고, 뒤이은 flush() 는 데코레이터에 남아 있을 수 있는 버퍼를 비운다.
3 입력 측 데코레이터를 만든다. 하부 소스는 시험 도우미 hello_world_inputstream() 이 돌려주는 hello, world 12 바이트 스트림이고, 안쪽에는 또 하나의 새 MessageDigest 인스턴스가 들어 있다. 출력 측과는 별개의 다이제스트라 reset() 이 필요 없다.
4 dis.transferTo(OutputStream.nullOutputStream()) 으로 12 바이트를 끝까지 읽어 버린다. 읽힌 바이트 자체는 버려지지만, 입력 측 MessageDigest 에는 그대로 누적된다. dis.readAllBytes() 와 달리 읽은 바이트를 배열 하나에 따로 모으지 않는다.
5 두 데코레이터에서 산출한 다이제스트가 같음을 시험한다. 출력 측과 입력 측 모두 같은 12 바이트를 같은 알고리즘으로 보냈으므로 같은 값이 나오는 것이 당연하다.

java.security.Signature

편지의 마지막에 남기는 친필 서명은 누가 썼는지를 밝히고, 그 사람이 내용에 동의했음을 보이며, 나중에 그 사실을 부인하지 못하게 한다. 디지털 세계에서는 전자 서명이 그 역할을 맡는다. 송신자가 자신만 가진 개인 키로 메시지에 서명하면, 수신자는 송신자의 공개 키로 그 서명이 정말 그 키의 소유자가 바로 그 메시지에 만든 것인지 검증한다. java.security.Signature 클래스는 이 전자 서명의 추상화이다. 알고리즘 이름과 키를 받아, 서명 값을 만드는 일과 그 서명을 검증하는 일을 같은 인터페이스로 제공한다.[6]

java.security.Signature
package java.security;

public abstract class Signature extends SignatureSpi {

    public final void update(byte[] data) throws SignatureException { ... }

    ...
}

Signature 인스턴스는 세 가지 상태를 가지는 상태 기계이다. (상태 열의 값은 Signature 클래스 안에 protected static final int 로 선언된 상수의 이름이다.)

상태 의미 전이 방법

UNINITIALIZED

getInstance(…​) 직후의 초기 상태이다. update(…​) 도 sign() 도 verify(…​) 도 부를 수 없다.

initSign(…​) 또는 initVerify(…​)

SIGN

서명 생성 모드이다. update(…​) 로 데이터를 누적한 뒤 sign() 으로 서명을 산출한다.

initSign(privateKey)

VERIFY

서명 검증 모드이다. update(…​) 로 데이터를 누적한 뒤 verify(signature) 로 일치 여부를 확인한다.

initVerify(publicKey)

MessageDigest 와 마찬가지로 알고리즘 이름으로 인스턴스를 얻고, 상태에 맞게 초기화한 뒤, update(…​) 로 입력을 누적시키고, sign() 또는 verify(…​) 로 결과를 받는다.

void update(byte[] data)

배열 전체의 바이트를 누적한다. update(data, 0, data.length) 와 같다. MessageDigest.update(byte[]) 와 시그니처가 같고 동작도 같지만, 인스턴스가 초기화되어 있지 않으면 (UNINITIALIZED 상태) SignatureException 을 던진다. HelloWorld#update(Signature) 는 hello, world 의 12 바이트를 이 메서드에 한 번에 넘긴다.[7]

분할 입력의 동등성은 Signature 에도 그대로 성립한다. Signature 도 여러 번 넣은 입력을 이어 붙인 하나의 데이터로 다루기 때문이다. 예를 들어 "SHA256withRSA" 알고리즘은 입력을 SHA-256 으로 누적 해싱해 두었다가, sign() / verify(…​) 시점에 비로소 그 해시값에 RSA 연산을 적용한다.

java.security.SecureRandom

java.security.SecureRandom 클래스는 암호학적으로 강한 난수 생성기 (RNG) 이다.[8] java.util.Random 을 확장하지만, 앞서 뽑힌 값들로부터 다음 값을 예측할 수 없어야 한다는 점이 다르다. 그래서 키, 솔트, 초기화 벡터처럼 남이 짐작해서는 안 되는 값을 만들 때 쓴다. 다른 엔진 클래스와 마찬가지로 알고리즘 이름을 받는 getInstance(…​) 로 인스턴스를 얻을 수 있고, 생성자 (new SecureRandom()) 로 기본 알고리즘의 인스턴스를 얻을 수도 있다.

java.security.SecureRandom
package java.security;

public class SecureRandom extends java.util.Random {

    public void setSeed(byte[] seed) { ... }

    ...
}

void setSeed(byte[] seed)

주어진 바이트들로 이 인스턴스의 시드를 다시 정한다. 메서드 이름과 달리 주어진 시드는 기존 시드를 대체하지 않고 보충한다. 그래서 이 메서드를 여러 번 호출해도 무작위성이 줄어들지 않는다. seed 가 null 이면 NullPointerException 을 던진다. HelloWorld#setSeed(SecureRandom) 은 hello, world 의 12 바이트를 이 메서드에 한 번에 넘긴다.[9]

보충이 아니라 시드의 전부가 되는 경우도 있다. 의사 난수 생성기 (PRNG) 방식의 SecureRandom 은 nextBytes(…​) 나 reseed() 보다 setSeed(…​) 가 먼저 호출되면 스스로 시드를 만들지 않는다. 이때는 호출자가 건넨 시드만으로 난수를 만들므로, 그 시드에 충분한 엔트로피가 들어 있는지는 호출자가 책임져야 한다.

update(MessageDigest)

HelloWorld 인터페이스의 update(MessageDigest) 메서드는 MessageDigest 를 확장한 형 (T) 의 인스턴스를 hello, world 12 바이트로 갱신한다. update(…​) 라는 이름대로 내부 해시 상태를 갱신한다. 최종 해시는 digest() 호출로 얻는다.

HelloWorld#update(MessageDigest)
<T extends MessageDigest> T update(T digest)

  • 주어진 메시지 다이제스트를 hello, world 바이트들로 갱신한다.

  • T (타입 매개변수): 호출자가 건넨 MessageDigest 의 구체 타입. 반환형도 같은 T 라서, 호출자는 자기가 건넨 서브타입을 캐스트 없이 다시 받는다.

  • digest (매개변수): hello, world 바이트로 갱신할 MessageDigest.

  • 반환값: 주어진 digest.

  • NullPointerException (예외): digest 가 null 인 경우.

  • 기본 구현: 다음과 같이 동작한다.

    • digest 가 null 인지를 호출 스레드에서 즉시 검사하여, NullPointerException 을 던진다.

    • 길이가 12 인 byte[] 를 만들고 set(array) 로 hello, world 바이트를 채운다.

    • 채워진 배열로 digest.update(array) 를 호출하여 digest 를 갱신한다.

이 메서드는 set(byte[]) 만 알면 구현할 수 있다. 12 바이트 배열을 만들고, set(array) 로 hello, world 를 채운 뒤, digest.update(array) 한 줄로 갱신한다. 해시 계산의 마무리와 결과 회수는 호출자의 책임이다. 호출자가 원하는 시점에 digest.digest() 로 직접 처리한다.

이미 구현되어 있는 본문은 아래와 같다.

HelloWorld#update(digest)
default <T extends MessageDigest> T update(final T digest) {
    Objects.requireNonNull(digest, "digest is null");
    final var array = new byte[BYTES];
    set(array);
    digest.update(array);
    return digest;
}

HelloWorld_Update_MessageDigest_Test

위 update(MessageDigest) 메서드를 검증하는 시험 클래스이다.

update(digest) 메서드가 set(array) 로 byte[12] 를 채우고, 그 배열로 digest.update(array) 를 호출하여 digest 를 갱신하는지를 검증한다.

HelloWorld_Update_MessageDigest_Test#__()
final var service = set_array_returns_the_array(service()); (1)
final var digest = mock(MessageDigest.class);
// ------------------------------------------------------------------------------------ when
final var result = service.update(digest);
// ------------------------------------------------------------------------------------ then
final var array = set_array12_invoked_once(service);        (2)
verify(digest, times(1)).update(array);                     (3)
assertSame(digest, result);
1 service.set(array) 가 호출되면 그 배열을 그대로 돌려주도록 스텁한다.
2 service.set(…​) 이 길이 12 의 배열로 정확히 한 번 호출되었는지 검증하고, 그때 전달된 배열 자체를 돌려받는다.
3 바로 그 배열로 digest.update(array) 가 정확히 한 번 호출되어 갱신되었는지 검증한다. 이름이 같은 다른 update(…​) 오버로드가 호출되었거나, 다른 배열로 갱신되었다면 시험이 실패한다.

표준 알고리즘

java.security.MessageDigest 의 API 문서는 모든 Java 플랫폼 구현이 반드시 지원해야 하는 표준 알고리즘으로 SHA-1, SHA-256, SHA-384 세 가지를 정해 둔다.[10] 아래는 이 세 알고리즘마다 MessageDigest 를 만들어 update(MessageDigest) 로 hello, world 를 넣은 뒤 digest() 로 얻은 해시를 출력한 결과이다.

표준 알고리즘별 hello, world 의 해시
SUN |                SHA-1 |  20( 160) | t+I+...HIQ=
SUN |              SHA-256 |  32( 256) | Ccp+...DVs=
SUN |              SHA-384 |  48( 384) | H822...DNt+

왼쪽부터 제공자, 알고리즘, 해시의 바이트 수와 비트 수, Base64 로 인코딩한 해시의 앞뒤 네 글자이다. 해시는 입력이 같으면 언제나 같으므로, 같은 알고리즘이라면 어느 환경에서 실행해도 같은 값이 나온다.

update(Signature)

HelloWorld 인터페이스에 정의된 update(Signature) 메서드는 Signature 를 확장한 형 (T) 의 인스턴스를 hello, world 12 바이트로 갱신한다. 서명을 산출하지도, 검증을 수행하지도 않는다. 갱신된 내부 상태를 유지하며, 서명 생성이나 검증은 이후 sign() / verify(…​) 호출로 수행한다.

HelloWorld#update(Signature)
<T extends Signature> T update(T signature) throws SignatureException

  • 주어진 서명 객체를 hello, world 바이트들로 갱신한다.

  • T (타입 매개변수): 호출자가 건넨 Signature 의 구체 타입. 반환형도 같은 T 라서, 호출자는 자기가 건넨 서브타입을 캐스트 없이 다시 받는다.

  • signature (매개변수): hello, world 바이트로 갱신할 Signature. 미리 initSign(…​) 또는 initVerify(…​) 로 초기화되어 있어야 한다.

  • 반환값: 주어진 signature.

  • NullPointerException (예외): signature 가 null 인 경우.

  • SignatureException (예외): signature 가 초기화되지 않은 상태이거나, 그 외 서명 처리 중 오류가 발생한 경우.

  • 기본 구현: 다음과 같이 동작한다.

    • signature 가 null 인지를 호출 스레드에서 즉시 검사하여, NullPointerException 을 던진다.

    • 길이가 12 인 byte[] 를 만들고 set(array) 로 hello, world 바이트를 채운다.

    • 채워진 배열로 signature.update(array) 를 호출하여 signature 를 갱신한다.

이 메서드는 update(MessageDigest) 와 형태가 똑같다. 12 바이트 배열을 만들고, set(array) 로 채운 뒤, signature.update(array) 한 줄로 갱신한다. signature 가 서명 모드인지 검증 모드인지, 어떤 키로 초기화되었는지는 이 메서드가 신경 쓰지 않는다. 그 설정은 호출자가 미리 해 둔다.

이미 구현되어 있는 본문은 아래와 같다.

HelloWorld#update(signature)
default <T extends Signature> T update(final T signature) throws SignatureException {
    Objects.requireNonNull(signature, "signature is null");
    final var array = new byte[BYTES];
    set(array);
    signature.update(array); (1)
    return signature;
}
1 set(…​) 으로 채워진 바로 그 배열로 서명 (혹은 검증) 누적기를 갱신한다. 서명 산출도 검증 결과 회수도 이 메서드의 책임이 아니다. 호출자가 원하는 시점에 signature.sign() 또는 signature.verify(…​) 로 직접 받아 가게 한다.

HelloWorld_Update_Signature_Test

위 update(Signature) 메서드를 검증하기 위한 시험 클래스이다.

update(signature) 메서드가 set(array) 로 byte[12] 를 채우고, 그 배열로 signature.update(array) 를 호출하여 signature 를 갱신하는지를 검증한다. 구현 절차가 update(MessageDigest) 와 동일하므로, 시험 클래스와 이 메서드 모두 이미 구현되어 있다.

HelloWorld_Update_Signature_Test#__()
final var service = set_array_returns_the_array(service()); (1)
final var signature = mock(Signature.class);
// ------------------------------------------------------------------------------------ when
final var result = service.update(signature);               (2)
// ------------------------------------------------------------------------------------ then
final var array = set_array12_invoked_once(service);        (3)
verify(signature, times(1)).update(array);                  (4)
assertEquals(signature, result);
1 service.set(array) 가 호출되면 그 배열을 그대로 돌려주도록 스텁한다.
2 service 모의 객체의 update(Signature) 메서드에 signature 모의 객체를 전달한다.
3 service.set(…​) 이 길이 12 의 배열로 정확히 한 번 호출되었는지 검증하고, 그때 전달된 배열 자체를 돌려받는다.
4 바로 그 배열로 signature.update(array) 가 정확히 한 번 호출되어 갱신되었는지 검증한다. 이름이 같은 다른 update(…​) 오버로드가 호출되었거나, 다른 배열로 갱신되었다면 시험이 실패한다.

HelloWorld#update(Signature) 는 서명할 때와 검증할 때 각각 한 번씩 부른다. 서명 측은 개인 키로 initSign(…​) 한 Signature 에, 검증 측은 공개 키로 initVerify(…​) 한 Signature 에 같은 12 바이트를 넣어야 verify(…​) 가 true 를 돌려준다.

final var signature = ...
// ------------------------------------------------------------------------------------ sign
...
service().update(signature);
final var signed = signature.sign();
// ---------------------------------------------------------------------------------- verify
...
service().update(signature);
final var verified = signature.verify(signed);
// ------------------------------------------------------------------------------------ then
assertTrue(verified);

표준 알고리즘

java.security.Signature 의 API 문서는 모든 Java 플랫폼 구현이 반드시 지원해야 하는 표준 알고리즘과 그 키 크기 또는 곡선을 정해 둔다.[11] 아래는 그 알고리즘마다 키 쌍을 만들어 위와 같이 서명하고 검증한 결과이다. 모든 줄에서 verify(…​) 는 true 를 돌려주었다.

표준 알고리즘별 hello, world 의 서명
         SHA1withDSA |      1024 |  46 | MCwC...bA==
       SHA256withDSA |      2048 |  62 | MDwC...RVA=
     SHA256withECDSA | secp256r1 |  70 | MEQC...OQ==
     SHA384withECDSA | secp384r1 | 104 | MGYC...foQ=
         SHA1withRSA |      2048 | 256 | fakm...1Q==
       SHA256withRSA |      2048 | 256 | Fjhs...WA==
       SHA384withRSA |      2048 | 256 | etNi...xA==
RSASSA-PSS (SHA-256) |      2048 | 256 | fxMy...tA==
RSASSA-PSS (SHA-384) |      2048 | 256 | hHTD...kg==

왼쪽부터 알고리즘, 키의 비트 수 또는 곡선 이름, 서명의 바이트 수, Base64 로 인코딩한 서명의 앞뒤 네 글자이다. RSA 계열의 서명은 키의 모듈러스와 같은 길이 (2048 비트, 즉 256 바이트) 가 된다. DSA 와 ECDSA 의 서명은 두 정수 r, s 를 DER 로 인코딩한 것이라 정수의 값에 따라 길이가 한두 바이트씩 달라질 수 있다. 키를 실행할 때마다 새로 만들고, DSA / ECDSA / RSASSA-PSS 는 서명할 때마다 난수를 쓰므로 서명의 값은 실행마다 다르다.

setSeed(SecureRandom)

HelloWorld 인터페이스의 setSeed(SecureRandom) 메서드는 SecureRandom 을 확장한 형 (T) 의 인스턴스에 hello, world 12 바이트를 시드로 보탠다. 메서드 이름은 setSeed(…​) 이지만 기존 시드를 바꾸지 않고 보충한다.

HelloWorld#setSeed(SecureRandom)
<T extends SecureRandom> T setSeed(T random)

  • 주어진 보안 난수 생성기의 시드를 hello, world 바이트들로 보충한다.

  • T (타입 매개변수): 호출자가 건넨 SecureRandom 의 구체 타입. 반환형도 같은 T 라서, 호출자는 자기가 건넨 서브타입을 캐스트 없이 다시 받는다.

  • random (매개변수): hello, world 바이트로 시드를 보충할 SecureRandom.

  • 반환값: 주어진 random.

  • NullPointerException (예외): random 이 null 인 경우.

  • 참고: SecureRandom.setSeed(byte[]) 메서드는 기존 시드를 대체하지 않고 보충한다. 따라서 이 메서드는 random 의 무작위성을 결코 줄이지 않는다.

  • 기본 구현: 다음과 같이 동작한다.

    • random 이 null 인지를 호출 스레드에서 즉시 검사하여, NullPointerException 을 던진다.

    • 길이가 12 인 byte[] 를 만들고 set(array) 로 hello, world 바이트를 채운다.

    • 채워진 배열로 random.setSeed(array) 를 호출하여 random 의 시드를 보충한다.

이 메서드는 update(MessageDigest) 와 형태가 같다. 12 바이트 배열을 만들고, set(array) 로 hello, world 를 채운 뒤, 그 배열을 random.setSeed(array) 에 넘긴다. 난수를 실제로 뽑는 일은 호출자의 몫이다. 호출자가 원하는 시점에 random.nextBytes(…​) 같은 메서드로 직접 뽑는다.

현재까지 구현된 상태는 아래와 같다. 값이 채워진 배열로 random 의 시드를 보충하기만 하면 된다.

HelloWorld#setSeed(random)
default <T extends SecureRandom> T setSeed(final T random) {
    Objects.requireNonNull(random, "random is null");
    final var array = new byte[BYTES];
    set(array);
    // TODO: <array> 로 <random> 의 시드를 보충한다.
    return random;

설치된 알고리즘

아래는 실행 환경에 설치된 제공자들이 지원하는 SecureRandom 알고리즘마다 인스턴스를 만들어 setSeed(SecureRandom) 으로 hello, world 를 시드로 보탠 뒤, nextBytes(…​) 로 12 바이트를 뽑아 출력한 결과이다. 알고리즘 목록은 Security.getAlgorithms("SecureRandom") 으로 얻었다.

알고리즘별로 뽑은 12 바이트
                    DRBG |      SUN | 4fa498cb6b4113b1a95d9493
              NATIVEPRNG |      SUN | 5ea24baf34f91628ff933a51
      NATIVEPRNGBLOCKING |      SUN | d6168fd09a1f2f220c6c6bcc
   NATIVEPRNGNONBLOCKING |      SUN | 5b222c7af5516cbe980ff735
                SHA1PRNG |      SUN | d0c91fdf196b16bbdd0205df

왼쪽부터 알고리즘, 제공자 이름, 16 진수로 나타낸 12 바이트이다. 설치된 알고리즘은 플랫폼마다 다르다. 위 결과는 macOS 에서 얻은 것이라 운영 체제의 난수 소스를 쓰는 NATIVEPRNG 계열이 보이며, Windows 에서는 이 행들이 나오지 않는다. 이 계열은 시드를 보충할 뿐 대체하지 않으므로, 같은 hello, world 를 보태더라도 뽑히는 바이트가 실행할 때마다 다르다.

SHA1PRNG 는 다르게 동작한다. SecureRandom.setSeed(byte[]) 의 API 문서에 따르면, 의사 난수 생성기 (PRNG) 는 nextBytes(…​) 나 reseed() 보다 setSeed(…​) 가 먼저 호출되면 스스로 시드를 만들지 않는다.[12] 이 경우 건넨 시드가 보충이 아니라 시드의 전부가 된다. 그래서 새로 만든 SHA1PRNG 인스턴스 두 개에 똑같이 hello, world 를 넣으면 두 인스턴스는 같은 바이트를 내놓는다. 아래는 이를 확인하는 시험이다.

새로 만든 SHA1PRNG 두 개가 같은 바이트를 내놓는지 확인
final var random1 = service().setSeed(SecureRandom.getInstance("SHA1PRNG"));
final var random2 = service().setSeed(SecureRandom.getInstance("SHA1PRNG"));
final var bytes1 = new byte[HelloWorld.BYTES];
final var bytes2 = new byte[HelloWorld.BYTES];
random1.nextBytes(bytes1);
random2.nextBytes(bytes2);
assertArrayEquals(bytes1, bytes2);
printf(random1, bytes1);

첫 nextBytes(…​) 전에 시드를 준 SHA1PRNG 는 그 시드에만 달려 있으므로, 같은 JDK 와 제공자 (SUN) 에서는 몇 번을 실행해도 같은 바이트가 나온다. 위 표의 SHA1PRNG 행과도 같은 값이다. 다른 JDK 나 제공자에서도 이 바이트열이 그대로 나온다는 보장은 없다.

새로 만든 SHA1PRNG 가 내놓은 12 바이트
                SHA1PRNG |      SUN | d0c91fdf196b16bbdd0205df

hello, world 는 누구나 아는 12 바이트이므로, 이렇게 시드를 처음 넣는 용도로 쓰면 뽑히는 바이트를 누구든 미리 계산할 수 있다. setSeed(SecureRandom) 은 이미 스스로 시드를 만든 인스턴스에 바이트를 보태는 용도로만 써야 안전하다.
