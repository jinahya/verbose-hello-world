java.util.zip.Checksum

체크섬(checksum)은 데이터 무결성을 검증하기 위해 계산하는 고정 길이 값이다. 데이터를 전송하거나 저장할 때 체크섬을 함께 기록해 두면, 나중에 동일한 알고리즘으로 다시 계산한 값과 비교하여 데이터가 손상되었는지 감지할 수 있다. java.util.zip.Checksum 은 이 체크섬 계산기의 추상화이다. 바이트를 점진적으로 공급(update)한 뒤 누적된 값을 long 으로 꺼내는(getValue) 누적기 형태를 갖는다.

java.util.zip.Checksum
package java.util.zip;

public interface Checksum {

    default public void update(byte[] b) { ... }

    ...
}

HelloWorld 가 쓰는 메서드는 바이트 배열 전체를 공급하는 update(byte[]) 하나다.

void update(byte[] b)

바이트 배열 전체를 체크섬 계산에 공급한다. 인터페이스의 기본 구현은 update(b, 0, b.length) 를 부른다. 바이트를 여러 번에 나눠 공급해도 한 번에 공급한 것과 같은 값이 누적되며, 누적된 값은 getValue() 로 꺼낸다. HelloWorld#update(Checksum) 은 hello, world 의 12 바이트를 이 메서드에 한 번에 넘긴다.[10]

update(Checksum)

HelloWorld 인터페이스에 정의된 update(Checksum) 메서드는 Checksum 을 구현하는 형 (T) 의 인스턴스에 hello, world 12 바이트를 한 번에 공급한다. 체크섬 값을 바로 꺼내지는 않고, 갱신된 누적 상태를 유지한다. getValue() 는 현재 값을 조회하며 상태를 초기화하지 않는다.

HelloWorld#update(Checksum)
<T extends Checksum> T update(T checksum)

  • 주어진 체크섬을 hello, world 바이트들로 갱신한다.

  • T (타입 매개변수): 호출자가 건넨 체크섬의 구체 타입. checksum 인자가 그대로 이 T 타입으로 반환되므로, 호출자는 자기가 건넨 서브타입 (예: CRC32, CRC32C, Adler32) 을 캐스트 없이 다시 받을 수 있다.

  • checksum (매개변수): hello, world 12 바이트를 공급할 체크섬 누적기. update 호출 이전·이후의 상태 모두 호출자의 책임이다.

  • 반환값: 주어진 checksum.

  • NullPointerException (예외): checksum 이 null 인 경우.

  • 기본 구현: 다음과 같이 동작한다.

    • checksum 의 null 을 즉시 검사하여 NullPointerException 을 던진다.

    • 길이가 12 인 byte[] 를 만들고 set(array) 로 hello, world 바이트를 채운다.

    • 채워진 배열 전체를 한 번에 checksum.update(array) 로 공급한다. 분할 누적이 아니라 한 번의 호출이다.

null 검증부터 set(array) 호출, checksum.update(array) 한 번의 공급, 그리고 checksum 반환까지 네 단계 모두 이미 들어 있어 본문 그대로 동작한다.

HelloWorld#update(checksum)
default <T extends Checksum> T update(final T checksum) {
    Objects.requireNonNull(checksum, "checksum is null");
    final var array = new byte[BYTES];
    set(array);
    checksum.update(array); (1)
    return checksum;
}
1 hello, world 바이트 배열 전체를 체크섬 계산에 한 번에 공급한다.

DeflaterOutputStream / InflaterInputStream

Deflater / Inflater 를 직접 쓰는 일은 번거롭다. 입력 공급, 종료 신호, 남은 출력을 꺼내는 반복문, 자원 해제까지 호출자가 모두 챙겨야 하기 때문이다. 표준 라이브러리는 이 일을 대신 해 주는 스트림 데코레이터를 제공한다.[11][12]

DeflaterOutputStream 과 InflaterInputStream 은 각각 하위 (underlying) OutputStream / InputStream 과 Deflater / Inflater 인스턴스를 받아 감싸는 데코레이터다. write() 또는 read() 를 부르면 내부의 Deflater / Inflater 가 압축과 복원을 처리하므로 호출자는 일반 스트림처럼 쓰면 된다. 내부 Deflater / Inflater 가 받는 level (압축 수준 0 ~ 9) 과 nowrap (zlib 래퍼를 뺄지 여부) 의 의미는 그대로이므로, 이 절은 DeflaterOutputStream 이 새로 도입하는 syncFlush 매개변수에 집중한다.

DeflaterOutputStream(OutputStream out, Deflater def, boolean syncFlush) 생성자가 받는 세 번째 매개변수는 flush() 의 동작을 결정한다.

  • syncFlush = false (기본): flush() 는 하위 스트림만 비운다. 압축기 내부에 대기 중인 입력은 다음 write() / finish() / close() 까지 그대로 남는다.

  • syncFlush = true: flush() 는 Deflater.deflate(buf, Deflater.SYNC_FLUSH) 를 호출해 대기 중인 입력을 즉시 압축해 내보내고, DEFLATE 의 sync 마커 (00 00 ff ff) 를 삽입한다. 수신측은 이 시점까지의 데이터를 바로 복원할 수 있다.

finish() 를 부르기 전에 부분 데이터를 실시간으로 보내야 하는 스트리밍 시나리오 (HTTP 청크 응답, WebSocket per-message-deflate[13], 라이브 로그 등) 에서 켠다. 매 flush 마다 sync 마커 (≥ 5 bytes) 와 강제 블록 종료에 따른 압축률 저하라는 비용이 있어, 짧은 입력마다 flush 하면 출력이 원본보다 커지기도 한다. 실시간으로 받아 줄 수신자가 분명히 있을 때만 의도적으로 켜는 옵션이다.

아래 시험은 nowrap 과 syncFlush 두 boolean 의 네 조합마다 level 10 가지를 순회한다. service() 는 시험 대상 HelloWorld 인스턴스를 돌려주고, service().write(dos) 는 hello, world 12 바이트를 주어진 출력 스트림에 쓴다. levelStream() 은 압축 수준 0 ~ 9 를 돌려주는 도우미이다. 호출 순서가 write → flush → finish 라 flush 시점에 Deflater 가 아직 대기 중인 입력을 들고 있으므로, syncFlush = true 면 SYNC_FLUSH 마커 (00 00 ff ff) 가 결과 바이트에 실제로 들어간다.

DeflaterOutputStream 으로 hello, world 압축 → InflaterInputStream 으로 복원
System.out.printf("level syncFlush nowrap size compressed%n");
final var baos = new ByteArrayOutputStream();
for (final int level : levelStream().toArray()) {
    final byte[] compressed;
    baos.reset();
    try (var deflater = new Deflater(level, nowrap);
         var dos = new DeflaterOutputStream(baos, deflater, syncFlush)) {
        service().write(dos);
        dos.flush();                                               (1)
        dos.finish(); // redundant; close() will do finish()       (2)
    }
    compressed = baos.toByteArray();
    System.out.printf("%5d %9b %6b %4d %s%n", level, syncFlush, nowrap,
                      compressed.length, HexFormat.of().formatHex(compressed));
    if (!nowrap) {
        assertZlibWrapped(compressed);                             (3)
    }
    try (var bais = new ByteArrayInputStream(compressed);
         var inflater = new Inflater(nowrap);
         var iis = new InflaterInputStream(bais, inflater)) {
        final var uncompressed = iis.readAllBytes();
        assert uncompressed.length == HelloWorld.BYTES;
        assertArrayEquals(hello_world_byte_array(), uncompressed); (4)
    }
}
1 이 시점에 Deflater 가 대기 중인 12 바이트를 들고 있다. syncFlush = true 면 dos.flush() 가 Deflater.deflate(buf, SYNC_FLUSH) 를 호출해 첫 블록을 BFINAL = 0 으로 내보내고 뒤에 00 00 ff ff 마커를 덧붙인다. syncFlush = false 면 Deflater 에는 아무 일도 일어나지 않는다.
2 스트림을 마감한다. syncFlush = false 면 대기 중인 12 바이트를 BFINAL = 1 인 블록 하나로 압축해 내보내고, syncFlush = true 면 BFINAL = 1 인 빈 마지막 블록을 덧붙여 DEFLATE 스트림을 끝낸다. try-with-resources 가 곧바로 부르는 dos.close() 도 finish() 를 하므로 이 호출은 없어도 되지만, 스트림이 끝나는 시점을 코드에 드러낸다.
3 nowrap = false 일 때만 결과가 RFC 1950 zlib 형식 (헤더 2 + Adler-32 4) 과 일치하는지 확인하는 도우미다. nowrap = true 의 출력은 래퍼 없는 raw DEFLATE 라 검증을 건너뛴다.
4 nowrap 을 맞춘 Inflater 로 풀면 네 조합 모두 원본 12 바이트가 그대로 돌아온다. SYNC_FLUSH 마커는 길이가 0 인 빈 블록일 뿐이라 복원 결과에 영향이 없다.

level 10 가지 × nowrap 2 가지 × syncFlush 2 가지 = 40 회 실행한다. syncFlush 와 nowrap 모두 결과 바이트에 영향을 미치므로 네 조합의 결과는 서로 다르다.

syncFlush = true 일 때의 DEFLATE 본문은 다음 세 부분으로 나뉜다.

  • 첫 블록 (BFINAL = 0): dos.flush() 시점에 Deflater 가 들고 있던 12 바이트를 압축해 내보낸 블록. level = 0 이면 stored 블록 17 바이트 (000c00f3ff68656c6c6f2c20776f726c64), level ≥ 1 이면 fixed Huffman 블록 14 바이트 (ca48cdc9c9d75128cf2fca490100). syncFlush = false 일 때 같은 위치의 본문과 첫 바이트만 다르다 (01 → 00, cb → ca). BFINAL 비트가 첫 바이트의 비트 0 에 들어가기 때문이다.

  • SYNC_FLUSH 마커 (00 00 ff ff): 빈 stored 블록 (BFINAL = 0, BTYPE = 00, length = 0) 을 끼워 넣어 수신측이 그 시점까지의 데이터를 즉시 복원할 수 있도록 한다. level = 0 에서는 byte-aligned 상태라 마커가 5 바이트 (000000ffff), level ≥ 1 에서는 fixed Huffman 블록 끝의 padding 비트에 마커의 첫 3 비트가 흡수돼 4 바이트 (0000ffff) 만 추가된다.

  • 종결 빈 블록 (BFINAL = 1): dos.finish() 가 덧붙이는 빈 블록. level = 0 에서는 stored 빈 블록 5 바이트 (010000ffff), level ≥ 1 에서는 fixed Huffman 빈 블록 2 바이트 (0300).

두 줄의 크기가 다른 건 stored 와 fixed Huffman 의 인코딩 방식이 달라서다. stored 는 길이 필드 (LEN 2 + NLEN 2) 가 강제라 빈 블록이라도 4 바이트가 그대로 더해진다 (1 바이트 헤더까지 합쳐 5 바이트). fixed Huffman 은 EOB 심볼 하나로 블록을 끝내므로 빈 블록이 헤더 3 비트 + EOB 7 비트 = 10 비트 → 2 바이트면 충분하다. sync 마커가 level = 0 에서 5 바이트인 이유도 같다. byte-aligned 상태에서 시작하니 LEN / NLEN 이 통째로 따라붙는다. level ≥ 1 에서는 fixed Huffman 블록 끝의 padding 비트가 마커의 첫 3 비트를 흡수해 LEN / NLEN 4 바이트만 추가된다.

총 오버헤드는 level = 0 일 때 +10 바이트 (17 → 27 DEFLATE 본문), level ≥ 1 일 때 +6 바이트 (14 → 20 DEFLATE 본문) 이다. 12 바이트를 한 번 쓰고 곧장 닫는 시나리오에서는 sync 마커와 종결 블록 비용만 그대로 더해질 뿐 이득이 없다. syncFlush 는 HTTP 청크 응답 / WebSocket per-message-deflate / 라이브 로그 같은 스트리밍 시나리오에서만 의미가 있다.

java.util.zip.GZIPOutputStream

java.util.zip.GZIPOutputStream 은 gzip 파일 포맷[14] 으로 데이터를 기록하는 출력 스트림이다. DeflaterOutputStream 을 상속하며 내부적으로 같은 raw DEFLATE 압축 방식을 쓰되, 그 앞뒤로 gzip 의 고정 10 바이트 헤더와 CRC-32 + 원본 길이의 8 바이트 트레일러를 자동으로 기록한다. DeflaterOutputStream 에 gzip 헤더와 트레일러 처리를 더한 클래스라고 볼 수 있다.[15]

java.util.zip.GZIPOutputStream
package java.util.zip;

public class GZIPOutputStream extends DeflaterOutputStream {

    ...
}

.gz 파일, .tar.gz 의 바깥 층, HTTP Content-Encoding: gzip 등에서 가장 흔히 만나는 형식이다. 복원은 대응하는 java.util.zip.GZIPInputStream 으로 감싸 read() 만 호출하면 된다. 헤더 파싱, raw DEFLATE 복원, CRC 검증이 모두 자동이다.

GZIP file format specification version 4.3 (RFC 1952)

RFC 1952[16] 는 1996년 5월에 발표된 IETF Informational RFC 로, gzip 파일 포맷을 규정한다. 압축 알고리즘 자체 (DEFLATE) 는 다루지 않으며, DEFLATE 스트림에 자신의 형식과 내용을 스스로 밝히는 정보를 붙여 파일이나 전송 단위로 묶는 방법을 정의한다. 매직 바이트로 시작하는 헤더와, 끝의 CRC-32 + 원본 길이로 무결성과 크기를 검증한다.

헤더 10 bytes (고정 길이, RFC 1952 §2.3.1[17]):

  • ID1 ID2 (2 bytes): 매직 0x1f 0x8b

  • CM (1 byte): 압축 방식 (8 = DEFLATE)

  • FLG (1 byte): 선택 필드 플래그

  • MTIME (4 bytes, little-endian): 원본 수정 시각 (0 = 미지정)

  • XFL (1 byte), OS (1 byte)

FLG 가 비트를 켜면 추가 길이·원본 파일명·주석·헤더 CRC 등이 헤더 뒤에 따라붙어 길이가 늘어난다. JDK 의 GZIPOutputStream 은 FLG = 0 으로 어떤 선택 필드도 쓰지 않아 항상 정확히 10 bytes 의 고정 헤더를 낸다.

트레일러 8 bytes (little-endian uint32 두 개):

  • CRC32 (4 bytes): 압축 전 원본의 CRC-32

  • ISIZE (4 bytes): 원본 길이 mod 232

zlib 래퍼와 비교하면 헤더가 2 → 10 bytes 로 길어지고, 트레일러가 Adler-32 4 bytes 에서 CRC-32 + ISIZE 8 bytes 로 바뀐다. 늘어난 만큼 파일 형식 스스로가 담는 정보 (매직·OS·시각) 와 더 강한 무결성 검사, 명시적인 원본 길이를 얻는다.

GZIPOutputStream 의 syncFlush

GZIPOutputStream 의 일부 생성자도 syncFlush 매개변수를 받는다. 의미와 득실은 DeflaterOutputStream 의 syncFlush 에서 설명한 것과 같다. 내부적으로 같은 Deflater.SYNC_FLUSH 방식을 쓴다.

RFC 1952 는 기본 압축 수준을 규정하지 않는다. 와이어 포맷만 정의하고, 수준 선택은 구현체에 맡긴다. 헤더의 XFL 바이트가 힌트로 2 (최대 압축) / 4 (가장 빠름) 을 표시할 수 있지만 권고일 뿐이라 무시해도 된다.

JDK 의 GZIPOutputStream 은 내부적으로 new Deflater(Deflater.DEFAULT_COMPRESSION, true) 를 쓴다. level = -1 이며, zlib 관례에 따라 level 6 으로 처리된다. 또한 XFL 은 수준과 상관없이 항상 0 으로 기록한다. 기본 수준 6 은 zlib compress2(…​ Z_DEFAULT_COMPRESSION), GNU gzip(1) (기본 -6) 등 대부분 구현이 따르는 사실상의 표준이며, 압축률과 속도의 절충점으로 널리 채택된 값이다.

시험은 GZIPOutputStream 의 두 번째 생성자 매개변수 syncFlush 를 켰을 때와 껐을 때를 write → flush → finish 호출 순서로 각각 한 번씩 돌려, syncFlush 가 결과 바이트에 영향을 주는지 확인한다. flush() 가 finish() 보다 먼저 불리므로 syncFlush = true 면 Deflater 에 아직 대기 중인 입력이 남은 상태에서 SYNC_FLUSH 가 일어나 결과가 길어진다.

GZIPOutputStream(baos, syncFlush) 으로 syncFlush 두 분기를 모두 시험
System.out.printf("syncFlush size compressed%n");
final var baos = new ByteArrayOutputStream();
try (var gzipos = new GZIPOutputStream(baos, syncFlush)) {
    service().write(gzipos);                                   (1)
    gzipos.flush();                                            (2)
    gzipos.finish(); // redundant; close() will do finish()    (3)
}
final var compressed = baos.toByteArray();
System.out.printf("%9b %4d %s%n", syncFlush,
                  compressed.length, HexFormat.of().formatHex(compressed));
assertGzipWrapped(compressed);                                 (4)
try (var bais = new ByteArrayInputStream(compressed);
     var gzipis = new GZIPInputStream(bais)) {
    final var uncompressed = gzipis.readAllBytes();
    assertArrayEquals(hello_world_byte_array(), uncompressed); (5)
}
1 12 바이트를 그대로 전달한다. 내부 Deflater 가 입력을 대기 중인 상태로 들고만 있으므로 baos 에는 생성자가 쓴 헤더 10 바이트만 기록되어 있다.
2 이 시점에 Deflater 가 대기 중인 12 바이트를 들고 있다. syncFlush = true 면 첫 블록을 BFINAL = 0 으로 내보내고 뒤에 00 00 ff ff 마커를 덧붙인다. syncFlush = false 면 아무 일도 일어나지 않는다.
3 스트림을 마감한다. BFINAL = 1 의 마지막 블록을 덧붙여 DEFLATE 본문을 닫고, 이어서 GZIPOutputStream 이 트레일러 (CRC-32 + ISIZE) 8 바이트를 기록한다. try-with-resources 가 곧바로 gzipos.close() 를 호출하므로 이 호출은 없어도 되지만, 스트림이 끝나는 시점을 코드에 드러낸다.
4 헤더 10 바이트가 RFC 1952 가 규정한 1f 8b 08 00 00 00 00 00 00 ff 와 일치하는지, 본문 + 트레일러가 최소 8 바이트인지 확인하는 도우미다.
5 두 분기 모두 GZIPInputStream 으로 풀면 원본 12 바이트가 그대로 돌아온다. SYNC_FLUSH 마커는 복원할 때 빈 블록으로 처리되어 결과에 영향이 없다.
