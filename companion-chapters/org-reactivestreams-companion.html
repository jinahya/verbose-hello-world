Reactive Streams JVM 1.0.4 명세가 네 인터페이스에 정한 API 설명과 규칙을 영문 원문과 우리말 번역으로 함께 싣는다.[1] 책의 org.reactivestreams 절은 규칙의 번호와 원문 링크만 싣는다. 이어서 책이 구현하지 않는 처리자 (Processor) 를 다룬다.

org.reactivestreams.Publisher<T>

API 명세

아래 표는 Publisher 의 메서드에 대한 API 명세를 원문과 번역으로 옮긴 것이다.[2]

Table 1. subscribe(Subscriber<? super T>): API 명세
구분 API 명세 한국어

설명

Request Publisher to start streaming data.

Publisher 에게 데이터 스트리밍을 시작하도록 요청한다.

This is a "factory method" and can be called multiple times, each time starting a new Subscription.

이는 팩토리 메서드이며 여러 번 호출될 수 있고, 매 호출마다 새 Subscription 을 시작한다.

Each Subscription will work for only a single Subscriber. A Subscriber should only subscribe once to a single Publisher.

각 Subscription 은 오직 하나의 Subscriber 를 위해서만 동작한다. 한 Subscriber 는 한 Publisher 에 오직 한 번만 구독해야 한다.

If the Publisher rejects the subscription attempt or otherwise fails it will signal the error via Subscriber.onError(Throwable).

Publisher 가 구독 시도를 거절하거나 그 외의 사유로 실패한다면, Subscriber.onError(Throwable) 을 통해 그 오류를 알린다.

매개변수 s

the Subscriber that will consume signals from this Publisher

이 Publisher 가 알리는 신호를 소비할 Subscriber.

규칙

발행자 규칙 [1.1] 부터 [1.11] 까지를 명세의 1절에서 옮겼다. 각 규칙 아래의 ※ 줄은 명세가 그 규칙에 붙인 의도 (intent) 설명이다.

Table 2. 발행자 규칙 (Publisher Rules)
ID Rule 한국어

1.1

The total number of onNext´s signalled by a Publisher to a Subscriber MUST be less than or equal to the total number of elements requested by that Subscriber´s Subscription at all times.

발행자가 한 구독자에게 알리는 onNext 의 총 개수는, 그 구독자의 구독이 요청한 원소 총 개수를 어느 시점에서도 초과해서는 안 된다.

※

The intent of this rule is to make it clear that Publishers cannot signal more elements than Subscribers have requested. There’s an implicit, but important, consequence to this rule: Since demand can only be fulfilled after it has been received, there’s a happens-before relationship between requesting elements and receiving elements.

이 규칙의 의도는 발행자가 구독자가 요청한 것보다 더 많은 원소를 전달할 수 없다는 점을 명확히 하는 데 있다. 이 규칙에는 암묵적이지만 중요한 결과가 따른다. 수요는 받은 뒤에야 충족될 수 있으므로, 원소를 요청하는 것과 받는 것 사이에는 happens-before 관계가 성립한다.

1.2

A Publisher MAY signal fewer onNext than requested and terminate the Subscription by calling onComplete or onError.

발행자는 요청한 것보다 적게 onNext 를 알리고 onComplete 또는 onError 로 그 구독을 종단시킬 수 있다.

※

The intent of this rule is to make it clear that a Publisher cannot guarantee that it will be able to produce the number of elements requested; it simply might not be able to produce them all; it may be in a failed state; it may be empty or otherwise already completed.

이 규칙의 의도는 발행자가 요청받은 만큼의 원소를 만들어 낼 수 있다고 보장하지 못한다는 점을 명확히 하는 데 있다. 단순히 모두 만들어 내지 못할 수도 있고, 실패 상태일 수도 있고, 비어 있거나 이미 종단된 상태일 수도 있다.

1.3

onSubscribe, onNext, onError and onComplete signaled to a Subscriber MUST be signaled serially.

구독자에게 전달되는 onSubscribe, onNext, onError, onComplete 는 직렬 (serially) 로 전달되어야 한다.

※

The intent of this rule is to permit the signalling of signals (including from multiple threads) if and only if a happens-before relation between each of the signals is established.

이 규칙의 의도는 (여러 스레드에서의 전달을 포함해) 신호를 전달하는 것을 허용하되, 각 신호 사이에 happens-before 관계가 성립할 때에 한해서만 허용하는 것이다.

1.4

If a Publisher fails it MUST signal an onError.

발행자가 실패한다면 onError 를 전달해야 한다.

※

The intent of this rule is to make it clear that a Publisher is responsible for notifying its Subscribers if it detects that it cannot proceed—Subscribers must be given a chance to clean up resources or otherwise deal with the Publisher´s failures.

이 규칙의 의도는 발행자가 진행할 수 없음을 감지했을 때 구독자에게 알릴 책임이 있음을 명확히 하는 데 있다. 구독자는 자원을 정리하거나 발행자의 실패에 대응할 기회를 얻어야 한다.

1.5

If a Publisher terminates successfully (finite stream) it MUST signal an onComplete.

발행자가 유한한 항목 발행으로 정상 완료한다면 onComplete 를 전달해야 한다.

※

The intent of this rule is to make it clear that a Publisher is responsible for notifying its Subscribers that it has reached a terminal state—Subscribers can then act on this information; clean up resources, etc.

이 규칙의 의도는 발행자가 종단 상태에 도달했음을 구독자에게 알릴 책임이 있음을 명확히 하는 데 있다. 그 정보를 바탕으로 구독자는 자원 정리 등의 후처리를 할 수 있다.

1.6

If a Publisher signals either onError or onComplete on a Subscriber, that Subscriber´s Subscription MUST be considered cancelled.

발행자가 구독자에게 onError 또는 onComplete 를 전달한 시점에서, 그 구독자의 구독은 취소된 것으로 간주되어야 한다.

※

The intent of this rule is to make sure that a Subscription is treated the same no matter if it was cancelled, the Publisher signalled onError or onComplete.

이 규칙의 의도는 구독이 취소되었든, 발행자가 onError 또는 onComplete 를 전달했든, 동일하게 다루어지도록 보장하는 데 있다.

1.7

Once a terminal state has been signaled (onError, onComplete) it is REQUIRED that no further signals occur.

종단 상태 (onError, onComplete) 가 전달된 뒤로는 어떤 추가 신호도 발생해서는 안 된다.

※

The intent of this rule is to make sure that onError and onComplete are the final states of an interaction between a Publisher and Subscriber pair.

이 규칙의 의도는 onError 와 onComplete 가 발행자와 구독자의 상호작용에서 최종 상태가 되도록 보장하는 데 있다.

1.8

If a Subscription is cancelled its Subscriber MUST eventually stop being signaled.

구독이 취소되면 그 구독자에게 가는 신호는 결국 (eventually) 멈춰야 한다.

※

The intent of this rule is to make sure that Publishers respect a Subscriber’s request to cancel a Subscription when Subscription.cancel() has been called. The reason for eventually is because signals can have propagation delay due to being asynchronous.

이 규칙의 의도는 Subscription.cancel() 이 호출되면 발행자가 구독자의 취소 요청을 존중하도록 보장하는 데 있다. 결국 (eventually) 이라는 표현을 쓴 이유는 비동기 특성상 신호에 전파 지연이 있을 수 있기 때문이다.

1.9

Publisher.subscribe MUST call onSubscribe on the provided Subscriber prior to any other signals to that Subscriber and MUST return normally, except when the provided Subscriber is null in which case it MUST throw a java.lang.NullPointerException to the caller, for all other situations the only legal way to signal failure (or reject the Subscriber) is by calling onError (after calling onSubscribe).

Publisher.subscribe 는 다른 어떤 신호보다 먼저 주어진 구독자에 대해 onSubscribe 를 호출해야 하며, 호출 자체는 정상 반환되어야 한다. 단, 주어진 구독자가 null 인 경우에는 호출자에게 java.lang.NullPointerException 을 던져야 하고, 그 외 모든 상황에서 실패 (또는 구독 거절) 를 알리는 유일한 합법적인 방법은 (onSubscribe 를 호출한 뒤) onError 를 호출하는 것이다.

※

The intent of this rule is to make sure that onSubscribe is always signalled before any of the other signals, so that initialization logic can be executed by the Subscriber when the signal is received. Also onSubscribe MUST only be called at most once. If the supplied Subscriber is null, there is nowhere else to signal this but to the caller, which means a java.lang.NullPointerException must be thrown. Examples of possible situations: A stateful Publisher can be overwhelmed, bounded by a finite number of underlying resources, exhausted, or in a terminal state.

이 규칙의 의도는 onSubscribe 가 다른 어떤 신호보다 항상 먼저 전달되도록 하여, 구독자가 신호를 받은 시점에 초기화 로직을 실행할 수 있게 하는 데 있다. 또한 onSubscribe 는 최대 한 번만 호출되어야 한다. 주어진 구독자가 null 이라면 이를 알릴 곳이 호출자뿐이므로 java.lang.NullPointerException 을 던져야 한다. 가능한 상황의 예: 상태를 가진 발행자가 과부하 상태, 하부 자원의 수가 유한해 한정되어 있는 상태, 고갈 상태, 또는 종단 상태일 수 있다.

1.10

Publisher.subscribe MAY be called as many times as wanted but MUST be with a different Subscriber each time.

Publisher.subscribe 는 원하는 만큼 호출될 수 있으나, 매 호출마다 서로 다른 구독자여야 한다.

※

The intent of this rule is to have callers of subscribe be aware that a generic Publisher and a generic Subscriber cannot be assumed to support being attached multiple times. Furthermore, it also mandates that the semantics of subscribe must be upheld no matter how many times it is called.

이 규칙의 의도는 subscribe 의 호출자가 일반적인 발행자와 일반적인 구독자가 여러 번 연결될 수 있다고 가정해서는 안 된다는 점을 인지하도록 하는 데 있다. 또한 몇 번이 호출되더라도 subscribe 의 의미가 지켜져야 함을 강제한다.

1.11

A Publisher MAY support multiple Subscriber´s and decides whether each Subscription is unicast or multicast.

발행자는 여러 구독자를 지원할 수 있으며, 각 구독이 유니캐스트인지 멀티캐스트인지를 스스로 결정한다.

※

The intent of this rule is to give Publisher implementations the flexibility to decide how many, if any, Subscribers they will support, and how elements are going to be distributed.

이 규칙의 의도는 발행자 구현체가 몇 명의 구독자를 (또는 아예 없도록) 지원할지, 그리고 원소를 어떻게 분배할지를 선택할 수 있도록 유연성을 부여하는 데 있다.

API 명세

아래 표는 Subscription 의 메서드에 대한 API 명세를 원문과 번역으로 옮긴 것이다.[3]

Table 3. request(long): API 명세
구분 API 명세 한국어

설명

No events will be sent by a Publisher until demand is signaled via this method.

이 메서드를 통해 수요가 알려지기 전까지 Publisher 는 어떠한 이벤트도 보내지 않는다.

It can be called however often and whenever needed—but if the outstanding cumulative demand ever becomes Long.MAX_VALUE or more, it may be treated by the Publisher as "effectively unbounded".

필요한 만큼 자주, 필요한 때마다 호출될 수 있다. 다만 미처리 누적 수요가 한 번이라도 Long.MAX_VALUE 이상이 되면, Publisher 는 이를 "사실상 무제한"으로 간주할 수 있다.

Whatever has been requested can be sent by the Publisher so only signal demand for what can be safely handled.

요청된 만큼은 Publisher 가 보낼 수 있으므로, 안전하게 처리할 수 있는 만큼만 수요로 알려야 한다.

A Publisher can send less than is requested if the stream ends but then must emit either Subscriber.onError(Throwable) or Subscriber.onComplete().

Publisher 는 발행이 끝나는 경우 요청보다 적게 보낼 수 있으며, 그때는 반드시 Subscriber.onError(Throwable) 또는 Subscriber.onComplete() 를 알려야 한다.

매개변수 n

the strictly positive number of elements to requests to the upstream Publisher

업스트림 Publisher 에 요청할, 반드시 양수인 원소 개수.
Table 4. cancel(): API 명세
구분 API 명세 한국어

설명

Request the Publisher to stop sending data and clean up resources.

Publisher 에게 데이터 전송을 중단하고 자원을 정리하도록 요청한다.

Data may still be sent to meet previously signalled demand after calling cancel.

cancel 호출 뒤에도 이미 알려진 수요를 충족하기 위해 데이터가 여전히 전달될 수 있다.

규칙

구독 규칙 [3.1] 부터 [3.17] 까지를 명세의 3절에서 옮겼다. 각 규칙 아래의 ※ 줄은 명세가 그 규칙에 붙인 의도 (intent) 설명이다.

Table 5. 구독 규칙 (Subscription Rules)
ID Rule 한국어

3.1

Subscription.request and Subscription.cancel MUST only be called inside of its Subscriber context.

Subscription.request 와 Subscription.cancel 은 해당 구독자의 컨텍스트 안에서만 호출되어야 한다.

※

The intent of this rule is to establish that a Subscription represents the unique relationship between a Subscriber and a Publisher. The Subscriber is in control over when elements are requested and when more elements are no longer needed.

이 규칙의 의도는 구독이 한 구독자와 한 발행자 사이의 유일한 관계를 표현함을 확립하는 데 있다. 언제 원소를 요청하고 언제 더 이상 필요 없는지는 구독자가 결정한다.

3.2

The Subscription MUST allow the Subscriber to call Subscription.request synchronously from within onNext or onSubscribe.

구독은 구독자가 onNext 또는 onSubscribe 안에서 동기적으로 Subscription.request 를 호출하는 것을 허용해야 한다.

※

The intent of this rule is to make it clear that implementations of request must be reentrant, to avoid stack overflows in the case of mutual recursion between request and onNext (and eventually onComplete / onError). This implies that Publishers can be synchronous, i.e. signalling onNext´s on the thread which calls request.

이 규칙의 의도는 request 의 구현이 재진입 가능해야 한다는 점을 명확히 하는 데 있다. request 와 onNext (그리고 결국 onComplete / onError) 사이의 상호 재귀로 인한 스택 오버플로를 방지하기 위해서다. 이는 동기 발행자가 가능함을 함의한다. 즉 request 를 호출한 스레드 위에서 onNext 를 전달할 수 있다.

3.3

Subscription.request MUST place an upper bound on possible synchronous recursion between Publisher and Subscriber.

Subscription.request 는 발행자와 구독자 사이에 발생할 수 있는 동기 재귀에 상한을 두어야 한다.

※

The intent of this rule is to complement [3.2] by placing an upper limit on the mutual recursion between request and onNext (and eventually onComplete / onError). Implementations are RECOMMENDED to limit this mutual recursion to a depth of 1 (ONE)—for the sake of conserving stack space. An example for undesirable synchronous, open recursion would be Subscriber.onNext → Subscription.request → Subscriber.onNext → …, as it otherwise will result in blowing the calling thread´s stack.

이 규칙의 의도는 [3.2] 를 보완하여 request 와 onNext (그리고 결국 onComplete / onError) 사이의 상호 재귀에 상한을 두는 데 있다. 구현체는 이 상호 재귀의 깊이를 1 (ONE)로 제한할 것이 권장된다 (스택 공간을 절약하기 위해). 바람직하지 않은 동기 무한 재귀의 예로는 Subscriber.onNext → Subscription.request → Subscriber.onNext → … 가 있다. 그대로 두면 호출 스레드에서 스택 오버플로가 발생한다.

3.4

Subscription.request SHOULD respect the responsivity of its caller by returning in a timely manner.

Subscription.request 는 호출자의 반응성을 존중하여 적시에 반환해야 한다 (SHOULD).

※

The intent of this rule is to establish that request is intended to be a non-obstructing method, and should be as quick to execute as possible on the calling thread, so avoid heavy computations and other things that would stall the caller´s thread of execution.

이 규칙의 의도는 request 가 논블로킹 메서드이며 호출 스레드 위에서 가능한 한 빠르게 실행되어야 함을 확립하는 데 있다. 따라서 호출자의 실행 스레드를 정체시킬 무거운 계산 등은 피해야 한다.

3.5

Subscription.cancel MUST respect the responsivity of its caller by returning in a timely manner, MUST be idempotent and MUST be thread-safe.

Subscription.cancel 은 호출자의 반응성을 존중하여 적시에 반환해야 하며, 멱등이어야 하고 스레드 안전해야 한다.

※

The intent of this rule is to establish that cancel is intended to be a non-obstructing method, and should be as quick to execute as possible on the calling thread, so avoid heavy computations and other things that would stall the caller´s thread of execution. Furthermore, it is also important that it is possible to call it multiple times without any adverse effects.

이 규칙의 의도는 cancel 이 논블로킹 메서드이며 호출 스레드 위에서 가능한 한 빠르게 실행되어야 함을 확립하는 데 있다. 무거운 계산 등은 피해야 한다. 또한 여러 번 호출되어도 부작용 없이 동작할 수 있어야 한다.

3.6

After the Subscription is cancelled, additional Subscription.request(long n) MUST be NOPs.

구독이 취소된 뒤의 추가 Subscription.request(long n) 호출은 아무 일도 하지 않아야 (NOP) 한다.

※

The intent of this rule is to establish a causal relationship between cancellation of a subscription and the subsequent non-operation of requesting more elements.

이 규칙의 의도는 구독 취소와 이후 더 이상의 원소 요청이 무효화되는 것 사이의 인과 관계를 확립하는 데 있다.

3.7

After the Subscription is cancelled, additional Subscription.cancel() MUST be NOPs.

구독이 취소된 뒤의 추가 Subscription.cancel() 호출도 아무 일도 하지 않아야 (NOP) 한다.

※

The intent of this rule is superseded by [3.5].

이 규칙의 의도는 [3.5] 가 이미 포섭한다.

3.8

While the Subscription is not cancelled, Subscription.request(long n) MUST register the given number of additional elements to be produced to the respective subscriber.

구독이 아직 취소되지 않은 동안, Subscription.request(long n) 은 주어진 개수만큼의 추가 원소가 해당 구독자에게 생산되도록 등록해야 한다.

※

The intent of this rule is to make sure that request-ing is an additive operation, as well as ensuring that a request for elements is delivered to the Publisher.

이 규칙의 의도는 request 가 누적되는 연산임을 보장하고, 원소 요청이 발행자에게 반드시 전달되도록 하는 데 있다.

3.9

While the Subscription is not cancelled, Subscription.request(long n) MUST signal onError with a java.lang.IllegalArgumentException if the argument is ⇐ 0. The cause message SHOULD explain that non-positive request signals are illegal.

구독이 아직 취소되지 않은 동안, Subscription.request(long n) 은 인자가 0 이하이면 java.lang.IllegalArgumentException 으로 onError 를 전달해야 한다. 원인 메시지에는 양수가 아닌 요청 신호는 불법이라고 설명해야 한다 (SHOULD).

※

The intent of this rule is to prevent faulty implementations to proceed operation without any exceptions being raised. Requesting a negative or 0 number of elements, since requests are additive, most likely to be the result of an erroneous calculation on the behalf of the Subscriber.

이 규칙의 의도는 결함이 있는 구현체가 예외를 일으키지 않고 그대로 진행하는 것을 방지하는 데 있다. 요청은 누적되는 연산이므로, 음수나 0 의 원소 개수를 요청한다는 것은 구독자 측에서 잘못된 계산의 결과일 가능성이 가장 높다.

3.10

While the Subscription is not cancelled, Subscription.request(long n) MAY synchronously call onNext on this (or other) subscriber(s).

구독이 아직 취소되지 않은 동안, Subscription.request(long n) 은 그 (또는 다른) 구독자에게 onNext 를 동기적으로 호출할 수도 있다 (MAY).

※

The intent of this rule is to establish that it is allowed to create synchronous Publishers, i.e. Publishers who execute their logic on the calling thread.

이 규칙의 의도는 동기 발행자 (호출 스레드 위에서 로직을 실행하는 발행자) 의 구현이 허용됨을 확립하는 데 있다.

3.11

While the Subscription is not cancelled, Subscription.request(long n) MAY synchronously call onComplete or onError on this (or other) subscriber(s).

구독이 아직 취소되지 않은 동안, Subscription.request(long n) 은 그 (또는 다른) 구독자에게 onComplete 또는 onError 를 동기적으로 호출할 수도 있다 (MAY).

※

The intent of this rule is to establish that it is allowed to create synchronous Publishers, i.e. Publishers who execute their logic on the calling thread.

이 규칙의 의도는 동기 발행자 (호출 스레드 위에서 로직을 실행하는 발행자) 의 구현이 허용됨을 확립하는 데 있다.

3.12

While the Subscription is not cancelled, Subscription.cancel() MUST request the Publisher to eventually stop signaling its Subscriber. The operation is NOT REQUIRED to affect the Subscription immediately.

구독이 아직 취소되지 않은 동안, Subscription.cancel() 은 발행자가 결국 그 구독자에게 신호를 전달하지 않도록 요청해야 한다. 이 연산이 즉시 Subscription 에 효력을 발생시킬 필요는 없다.

※

The intent of this rule is to establish that the desire to cancel a Subscription is eventually respected by the Publisher, acknowledging that it may take some time before the signal is received.

이 규칙의 의도는 구독을 취소하려는 의사가 결국에는 발행자에 의해 존중됨을 확립하는 데 있다. 다만 신호가 수신되기까지 시간이 걸릴 수 있음을 인정한다.

3.13

While the Subscription is not cancelled, Subscription.cancel() MUST request the Publisher to eventually drop any references to the corresponding subscriber.

구독이 아직 취소되지 않은 동안, Subscription.cancel() 은 발행자가 결국 해당 구독자에 대한 모든 참조를 해제하도록 요청해야 한다.

※

The intent of this rule is to make sure that Subscribers can be properly garbage-collected after their subscription no longer being valid. Re-subscribing with the same Subscriber object is discouraged, but this specification does not mandate that it is disallowed since that would mean having to store previously cancelled subscriptions indefinitely.

이 규칙의 의도는 구독이 더 이상 유효하지 않게 된 뒤 구독자가 제대로 가비지 컬렉션 될 수 있도록 보장하는 데 있다. 같은 Subscriber 객체로 재구독하는 것은 권장되지 않으나, 본 명세가 이를 금지하지는 않는다. 금지하려면 이미 취소된 구독을 무기한 저장해야 하기 때문이다.

3.14

While the Subscription is not cancelled, calling Subscription.cancel MAY cause the Publisher, if stateful, to transition into the shut-down state if no other Subscription exists at this point.

구독이 아직 취소되지 않은 동안, Subscription.cancel 호출은 (발행자가 상태를 가진다면) 그 시점에 다른 구독이 존재하지 않을 경우 발행자를 종료 상태(shut-down)로 전환시킬 수도 있다.

※

The intent of this rule is to allow for Publishers to signal onComplete or onError following onSubscribe for new Subscribers in response to a cancellation signal from an existing Subscriber.

이 규칙의 의도는 기존 구독자의 취소 신호에 대응하여, 발행자가 새 구독자에게 onSubscribe 직후 onComplete 또는 onError 를 전달할 수 있도록 허용하는 데 있다.

3.15

Calling Subscription.cancel MUST return normally.

Subscription.cancel 호출은 반드시 정상 반환되어야 한다.

※

The intent of this rule is to disallow implementations to throw exceptions in response to cancel being called.

이 규칙의 의도는 cancel 호출에 대해 구현체가 예외를 던지지 못하도록 금지하는 데 있다.

3.16

Calling Subscription.request MUST return normally.

Subscription.request 호출은 반드시 정상 반환되어야 한다.

※

The intent of this rule is to disallow implementations to throw exceptions in response to request being called.

이 규칙의 의도는 request 호출에 대해 구현체가 예외를 던지지 못하도록 금지하는 데 있다.

3.17

A Subscription MUST support an unbounded number of calls to request and MUST support a demand up to 2^63-1 (java.lang.Long.MAX_VALUE). A demand equal or greater than 2^63-1 (java.lang.Long.MAX_VALUE) MAY be considered by the Publisher as "effectively unbounded".

구독은 request 의 무제한 호출을 지원해야 하며, 2^63-1 (java.lang.Long.MAX_VALUE) 까지의 수요를 지원해야 한다. 2^63-1 (java.lang.Long.MAX_VALUE) 이상의 수요는 발행자가 "사실상 무제한" 으로 간주할 수도 있다.

※

The intent of this rule is to establish that the Subscriber can request an unbounded number of elements, in any increment above 0, in any number of invocations of request. As it is not feasibly reachable with current or foreseen hardware within a reasonable amount of time (1 element per nanosecond would take 292 years) to fulfill a demand of 2^63-1, it is allowed for a Publisher to stop tracking demand beyond this point.

이 규칙의 의도는 구독자가 0 보다 큰 어떠한 증분으로든, request 의 어떠한 호출 횟수로도 무제한 개수의 원소를 요청할 수 있음을 확립하는 데 있다. 2^63-1의 수요를 충족하는 것이 현재 또는 예측 가능한 하드웨어로는 합리적 시간 안에 도달 불가능하므로 (1 원소/나노초로도 292 년이 걸린다), 발행자는 이 지점 이상에서 수요 추적을 중단할 수 있다.

규칙

구독자 규칙 [2.1] 부터 [2.13] 까지를 명세의 2절에서 옮겼다. 각 규칙 아래의 ※ 줄은 명세가 그 규칙에 붙인 의도 (intent) 설명이다.

Table 10. 구독자 규칙 (Subscriber Rules)
ID Rule 한국어

2.1

A Subscriber MUST signal demand via Subscription.request(long n) to receive onNext signals.

구독자는 onNext 신호를 받으려면 Subscription.request(long n) 으로 수요를 알려야 한다.

※

The intent of this rule is to establish that it is the responsibility of the Subscriber to decide when and how many elements it is able and willing to receive. To avoid signal reordering caused by reentrant Subscription methods, it is strongly RECOMMENDED for synchronous Subscriber implementations to invoke Subscription methods at the very end of any signal processing. It is RECOMMENDED that Subscribers request the upper limit of what they are able to process, as requesting only one element at a time results in an inherently inefficient "stop-and-wait" protocol.

이 규칙의 의도는 언제 몇 개의 원소를 받을 수 있고 받을 의향이 있는지를 구독자가 결정할 책임이 있음을 확립하는 데 있다. 재진입성 Subscription 메서드 호출에 의한 신호 순서 뒤바뀜을 피하기 위해, 동기 구독자 구현체는 신호 처리의 맨 마지막에 Subscription 메서드를 호출할 것이 강력히 권장된다. 또한 한 번에 하나씩 요청하면 본질적으로 비효율적인 "정지-대기" 프로토콜이 되므로, 처리 가능한 상한을 요청할 것이 권장된다.

2.2

If a Subscriber suspects that its processing of signals will negatively impact its Publisher´s responsivity, it is RECOMMENDED that it asynchronously dispatches its signals.

구독자가 자신의 신호 처리가 발행자의 반응성에 악영향을 줄 것으로 의심된다면, 비동기로 신호를 디스패치할 것이 권장된다 (RECOMMENDED).

※

The intent of this rule is that a Subscriber should not obstruct the progress of the Publisher from an execution point-of-view. In other words, the Subscriber should not starve the Publisher from receiving CPU cycles.

이 규칙의 의도는 구독자가 실행 관점에서 발행자의 진행을 방해해서는 안 된다는 것이다. 다시 말해, 구독자가 CPU 사이클을 차지해 발행자를 기아 상태로 만들어서는 안 된다.

2.3

Subscriber.onComplete() and Subscriber.onError(Throwable t) MUST NOT call any methods on the Subscription or the Publisher.

Subscriber.onComplete() 와 Subscriber.onError(Throwable t) 는 Subscription 또는 Publisher 의 어떤 메서드도 호출해서는 안 된다.

※

The intent of this rule is to prevent cycles and race-conditions—between Publisher, Subscription and Subscriber—during the processing of completion signals.

이 규칙의 의도는 종단 신호 처리 중에 발행자·구독·구독자 사이의 사이클과 경쟁 조건이 발생하는 것을 방지하는 데 있다.

2.4

Subscriber.onComplete() and Subscriber.onError(Throwable t) MUST consider the Subscription cancelled after having received the signal.

Subscriber.onComplete() 또는 Subscriber.onError(Throwable t) 를 받은 시점부터 구독자는 그 구독이 취소된 것으로 간주해야 한다.

※

The intent of this rule is to make sure that Subscribers respect a Publisher’s terminal state signals. A Subscription is simply not valid anymore after an onComplete or onError signal has been received.

이 규칙의 의도는 구독자가 발행자의 종단 상태 신호를 존중하도록 보장하는 데 있다. onComplete 또는 onError 가 수신된 뒤에는 그 구독은 더 이상 유효하지 않다.

2.5

A Subscriber MUST call Subscription.cancel() on the given Subscription after an onSubscribe signal if it already has an active Subscription.

이미 활성 구독을 보유한 구독자는, onSubscribe 신호로 또 다른 Subscription 을 받았다면 그 주어진 Subscription 에 대해 cancel() 을 호출해야 한다.

※

The intent of this rule is to prevent that two, or more, separate Publishers from trying to interact with the same Subscriber. Enforcing this rule means that resource leaks are prevented since extra Subscriptions will be cancelled. Failure to conform to this rule may lead to violations of Publisher rule 1, amongst others. Such violations can lead to hard-to-diagnose bugs.

이 규칙의 의도는 둘 이상의 별개 발행자가 같은 구독자와 상호작용하려는 상황을 막는 데 있다. 이 규칙을 강제하면 여분의 구독이 취소되므로 자원 누수가 방지된다. 이 규칙을 어기면 Publisher 규칙 1 위반 등으로 이어질 수 있으며, 진단하기 어려운 버그의 원인이 된다.

2.6

A Subscriber MUST call Subscription.cancel() if the Subscription is no longer needed.

구독자는 그 구독이 더 이상 필요 없으면 Subscription.cancel() 을 호출해야 한다.

※

The intent of this rule is to establish that Subscribers cannot just throw Subscriptions away when they are no longer needed, they have to call cancel so that resources held by that Subscription can be safely, and timely, reclaimed. An example of this would be a Subscriber which is only interested in a specific element, which would then cancel its Subscription to signal its completion to the Publisher.

이 규칙의 의도는 구독자가 더 이상 필요 없다는 이유만으로 Subscription 을 단순히 버려서는 안 되고, cancel 을 호출해 그 구독이 보유한 자원이 안전하고 시의적절하게 회수되도록 해야 함을 확립하는 데 있다. 예를 들어 특정 원소에만 관심이 있는 구독자는, 그 원소를 받은 뒤 Subscription 을 취소하여 발행자에게 완료를 알린다.

2.7

A Subscriber MUST ensure that all calls on its Subscription’s request and cancel methods are performed serially.

구독자는 자신의 구독에 대한 request 와 cancel 호출이 모두 직렬 (serially) 로 수행되도록 보장해야 한다.

※

The intent of this rule is to permit the calling of the request and cancel methods (including from multiple threads) if and only if a serial relation between each of the calls is established.

이 규칙의 의도는 (여러 스레드에서의 호출을 포함해) request 와 cancel 호출을 허용하되, 각 호출 사이에 직렬 관계가 성립할 때에 한해서만 허용하는 것이다.

2.8

A Subscriber MUST be prepared to receive one or more onNext signals after having called Subscription.cancel() if there are still requested elements pending. Subscription.cancel() does not guarantee to perform the underlying cleaning operations immediately.

구독자는 Subscription.cancel() 을 호출한 뒤에도 요청해 둔 원소가 남아 있는 동안에는 하나 이상의 onNext 신호를 받을 준비가 되어 있어야 한다. Subscription.cancel() 은 내부 정리 작업의 즉시 수행을 보장하지 않는다.

※

The intent of this rule is to highlight that there may be a delay between calling cancel and the Publisher observing that cancellation.

이 규칙의 의도는 cancel 을 호출한 시점과 발행자가 그 취소를 관측하는 시점 사이에 지연이 있을 수 있음을 강조하는 데 있다.

2.9

A Subscriber MUST be prepared to receive an onComplete signal with or without a preceding Subscription.request(long n) call.

구독자는 선행하는 Subscription.request(long n) 호출 없이도 onComplete 신호를 받을 준비가 되어 있어야 한다.

※

The intent of this rule is to establish that completion is unrelated to the demand flow—this allows for streams which complete early, and obviates the need to poll for completion.

이 규칙의 의도는 완료가 수요와 무관함을 확립하는 데 있다. 이는 조기에 완료되는 스트림을 허용하며, 완료 여부를 능동적으로 폴링할 필요가 없게 한다.

2.10

A Subscriber MUST be prepared to receive an onError signal with or without a preceding Subscription.request(long n) call.

구독자는 선행하는 Subscription.request(long n) 호출 없이도 onError 신호를 받을 준비가 되어 있어야 한다.

※

The intent of this rule is to establish that Publisher failures may be completely unrelated to signalled demand. This means that Subscribers do not need to poll to find out if the Publisher will not be able to fulfill its requests.

이 규칙의 의도는 발행자의 실패가 전달된 수요와 완전히 무관할 수 있음을 확립하는 데 있다. 따라서 구독자는 발행자가 요청을 충족하지 못할지 여부를 능동적으로 폴링할 필요가 없다.

2.11

A Subscriber MUST make sure that all calls on its signal methods happen-before the processing of the respective signals. I.e. the Subscriber must take care of properly publishing the signal to its processing logic.

구독자는 자신의 신호 메서드 호출이 그에 대응하는 신호의 처리에 happens-before 관계를 갖도록 보장해야 한다. 즉, 신호를 처리 로직에 제대로 게시하는 것을 구독자가 처리한다.

※

The intent of this rule is to establish that it is the responsibility of the Subscriber implementation to make sure that asynchronous processing of its signals are thread safe. See JMM definition of Happens-Before in section 17.4.5.

이 규칙의 의도는 구독자 구현체가 신호의 비동기 처리를 스레드 안전하게 만들 책임이 있음을 확립하는 데 있다. Happens-Before의 JMM 정의는 §17.4.5 를 참조한다.

2.12

Subscriber.onSubscribe MUST be called at most once for a given Subscriber (based on object equality).

주어진 구독자에 대해 (객체 동등성 기준으로) Subscriber.onSubscribe 는 최대 한 번 호출되어야 한다.

※

The intent of this rule is to establish that it MUST be assumed that the same Subscriber can only be subscribed at most once. Note that object equality is a.equals(b).

이 규칙의 의도는 같은 구독자는 최대 한 번만 구독될 수 있다고 가정해야 함을 확립하는 데 있다. 객체 동등성은 a.equals(b) 임에 유의한다.

2.13

Calling onSubscribe, onNext, onError or onComplete MUST return normally except when any provided parameter is null in which case it MUST throw a java.lang.NullPointerException to the caller, for all other situations the only legal way for a Subscriber to signal failure is by cancelling its Subscription. In the case that this rule is violated, any associated Subscription to the Subscriber MUST be considered as cancelled, and the caller MUST raise this error condition in a fashion that is adequate for the runtime environment.

onSubscribe, onNext, onError, onComplete 호출은 반드시 정상 반환되어야 한다. 단, 주어진 인자가 null 인 경우에는 호출자에게 java.lang.NullPointerException 을 던져야 하며, 그 외 모든 상황에서 구독자가 실패를 알리는 유일한 합법적인 방법은 자신의 Subscription 을 취소하는 것이다. 이 규칙이 위반된 경우, 해당 구독자와 연관된 모든 Subscription 은 취소된 것으로 간주되어야 하며, 호출자는 런타임 환경에 적합한 방식으로 이 오류 상황을 표명해야 한다.

※

The intent of this rule is to establish the semantics for the methods of Subscriber and what the Publisher is allowed to do in which case this rule is violated. «Raise this error condition in a fashion that is adequate for the runtime environment» could mean logging the error—or otherwise make someone or something aware of the situation—as the error cannot be signalled to the faulty Subscriber.

이 규칙의 의도는 구독자 메서드의 의미와, 이 규칙이 위반된 경우 발행자에게 허용되는 동작을 확립하는 데 있다. "런타임 환경에 적합한 방식으로 이 오류 상황을 표명" 한다는 것은 결함이 있는 구독자에게 그 오류를 신호로 보낼 수 없으므로, 오류를 로그로 남기거나 누군가/어떤 것에 상황을 알리는 것 등을 의미할 수 있다.

org.reactivestreams.Processor<T, R>

org.reactivestreams.Processor<T, R> [5] 인터페이스는 Reactive Streams 명세가 정의하는 네 인터페이스 중 처리 단계를 표현한다. 한쪽 끝에서는 구독자로, 다른 쪽 끝에서는 발행자로 동시에 동작하며, 두 인터페이스를 그대로 확장한 결합 인터페이스일 뿐 자신만의 메서드는 추가로 정의하지 않는다.

타입 매개변수 T 는 구독자로서 상위 발행자에게 요청하여 받는 항목의 타입, R 은 발행자의 입장에서 하위 구독자(들)에게 발행하는 타입이다. 둘이 같을 수도 (Processor<T, T>, 필터·로깅 등의 단순 통과 변형), 서로 다를 수도 (변환·디코딩·집계 등의 형 변환 변형) 있다.

처리자는 구독자와 발행자의 두 계약을 모두 따라야 한다. 즉, 자신에게 들어오는 신호는 명세 2절의 구독자 (Subscriber) 규칙을, 자신이 내보내는 신호는 명세 1절의 발행자 (Publisher) 규칙을 모두 만족해야 한다. 변환·필터링·합류·분기가 모두 이 단계에서 일어난다.

처리자가 다운스트림 측을 다루는 방식으로는 유니캐스트 (unicast) 와 멀티캐스트 (multicast) 두 가지가 모두 명세상 허용된다 (Publisher 규칙 1.11).

  • 멀티캐스트 처리자. 한 처리자 인스턴스가 업스트림 발행자에 한 번 구독하고, 여러 다운스트림 구독자가 같은 처리자에 구독하여 같은 항목을 함께 받는다. 처리자가 다운스트림으로 항목을 팬아웃 (fan-out) 한다. 명세 4절의 비공식 주석에서 "마지막 구독자"라는 표현이 가리키는 형태이다.

  • 유니캐스트 처리자. 한 처리자 인스턴스가 다운스트림 구독자 하나에 항목을 보낸다. 여러 다운스트림 구독자를 지원하려면 구독자마다 새 처리자 인스턴스를 만들어 업스트림에 별도로 구독하게 할 수 있다. 다운스트림 구독자 하나와 처리자 하나가 일대일로 묶인다.

업스트림 측은 어느 경우든 한 처리자 인스턴스가 한 번에 하나의 활성 구독만 보유한다 (Subscriber 규칙 2.5). 다만 유니캐스트 처리자 패턴은 별개 인스턴스 각각이 자신의 업스트림 구독을 가지므로, 업스트림 입장에서는 여러 처리자가 잇따라 (또는 동시에) 구독하는 형태로 보인다. 신호가 실제로 어떻게 전달되는지는 업스트림이 콜드 (cold) 발행자인지 핫 (hot) / 멀티캐스트 발행자인지에 따라 달라진다.

처리자가 지켜야 할 규칙은 Reactive Streams JVM 명세의 4절에 있다.[6] 처리자가 업스트림/다운스트림 구독에서 어떻게 맞물리는지를 시나리오별 시퀀스 도식으로 정리한다. 단순 통과, 업스트림 오류 전파, 업스트림 오류 복구, 다운스트림 측 취소의 업스트림 전파의 네 가지를 한 장씩 따로 그렸다.

단순 통과 (pass-through)

처리자가 업스트림 발행자로부터 받은 항목을 그대로 또는 변환하여 다운스트림 구독자에게 전달한다. 업스트림 onComplete 가 도착하면 처리자도 다운스트림 구독자에게 onComplete 를 전달하여 양쪽 구독이 함께 정상 종단된다.

업스트림 오류의 전파 (propagate upstream onError)

업스트림 발행자가 onError(t) 를 보내면, 처리자가 그 오류를 복구하지 않는 한 즉시 자신의 다운스트림 구독자에게 같은 onError(t) 를 전달해야 한다 (규칙 4.2).

업스트림 오류의 복구 (recover upstream onError)

처리자가 업스트림 onError 를 복구하기로 선택한 경우 (규칙 4.2 MAY), 자신은 그 업스트림 구독을 취소된 것으로 간주하고 (즉, 더 이상 그 구독에 의지하지 않고), 다운스트림으로는 자체적으로 결정한 후속 신호를 보낸다. 후속 신호는 명세 규칙을 지키는 범위에서 처리자가 정한다. 예를 들어 대체 항목 + onComplete 를 보내거나 다른 업스트림에 다시 구독할 수 있다.

다운스트림 측 취소의 업스트림 전파 (cancel propagation)

처리자의 마지막 다운스트림 구독자가 자신의 구독을 취소했을 때, 처리자가 자신의 업스트림 구독을 함께 취소하여 취소 신호가 업스트림으로 거슬러 올라가도록 하는 것이 권장되는 패턴이다.[7] 명세상 의무는 아니지만, 자원 회수와 구독 정리를 위해 일반적으로 따른다.

규칙

처리자 규칙 [4.1] 과 [4.2] 를 명세의 4절에서 옮겼다. 각 규칙 아래의 ※ 줄은 명세가 그 규칙에 붙인 의도 (intent) 설명이다.

Table 11. 처리자 규칙 (Processor Rules)
ID Rule 한국어

4.1

A Processor represents a processing stage—which is both a Subscriber and a Publisher and MUST obey the contracts of both.

처리자는 처리 단계를 표현하며, 구독자이자 발행자로서 두 인터페이스의 계약을 모두 따라야 한다.

※

The intent of this rule is to establish that Processors behave, and are bound by, both the Publisher and Subscriber specifications.

이 규칙의 의도는 처리자가 Publisher 명세와 Subscriber 명세 양쪽에 모두 구속되어 동작함을 확립하는 데 있다.

4.2

A Processor MAY choose to recover an onError signal. If it chooses to do so, it MUST consider the Subscription cancelled, otherwise it MUST propagate the onError signal to its Subscribers immediately.

처리자는 onError 신호를 복구하기로 선택할 수도 있다 (MAY). 그렇게 선택한 경우에는 해당 구독을 취소된 것으로 간주해야 하며, 그렇지 않다면 즉시 자신의 구독자들에게 그 onError 신호를 전파해야 한다.

※

The intent of this rule is to inform that it’s possible for implementations to be more than simple transformations.

이 규칙의 의도는 처리자 구현체가 단순한 변환에 그치지 않고 더 풍부한 동작을 할 수 있음을 알리는 데 있다.
