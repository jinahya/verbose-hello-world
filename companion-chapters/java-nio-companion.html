Direct buffer 를 쓸 때

Direct buffer 는 ByteBuffer.allocateDirect(int) 로 만드는 ByteBuffer 로, 그 내용이 가비지 컬렉터가 관리하는 JVM 힙 밖(off-heap)의 네이티브 메모리에 있을 수 있다.[1] ByteBuffer 의 API 문서에 따르면 JVM 은 direct buffer 에 대해 운영 체제의 네이티브 I/O 연산을 버퍼에 바로 수행하려고 최선을 다한다. 네이티브 I/O 호출 앞뒤로 버퍼의 내용을 중간 버퍼에 복사하는 일을 피하려 한다는 뜻이다. OpenJDK 는 힙 버퍼로 채널 I/O 를 하면 내용을 임시 direct buffer 로 복사한 뒤 네이티브 I/O 를 호출하므로, direct buffer 를 쓰면 이 복사를 줄일 수 있다.

대신 direct buffer 는 보통 힙 버퍼보다 할당과 해제 비용이 조금 더 크다. 또 내용이 힙 밖에 있을 수 있어서, 응용 프로그램의 메모리 사용량에 미치는 영향이 잘 드러나지 않는다. 그래서 API 문서는 direct buffer 를 주로 네이티브 I/O 에 쓰이는 크고 오래 쓰는 버퍼에 할당하고, 일반적으로는 프로그램의 성능이 측정할 수 있을 만큼 좋아질 때만 쓰라고 권한다.

HotSpot JVM 에서 쓸 수 있는 direct 메모리의 총량은 -XX:MaxDirectMemorySize 옵션으로 제한하며, 지정하지 않으면 최대 힙 크기(-Xmx)를 기준으로 정해진다. 이 한도를 넘겨 할당하려 하면 OutOfMemoryError 가 발생한다. 수명이 짧은 일회성 버퍼라면 힙 버퍼(ByteBuffer.allocate(int))가 더 효율적인 경우가 많다.

버퍼의 상태를 바꾸는 메서드

ByteBuffer (그 부모인 java.nio.Buffer) 는 capacity, limit, position, mark 네 개의 값을 상태로 가지며, 이들 사이에는 다음 관계가 성립한다.[2]

0 <= mark <= position <= limit <= capacity

(mark 가 정의되지 않은 상태일 때는 -1 이며, 위 관계에서 제외된다.)

방금 채운 영역을 읽을 수 있도록 limit 을 position 으로, position 을 0 으로 바꾸는 flip() 과 position, limit 을 직접 지정하는 position(int), limit(int) 외에도, 이 네 값을 한 번에 일관되게 바꾸는 메서드가 더 있다. 버퍼를 다시 채울 준비를 하는 clear(), 정해진 영역을 처음부터 다시 다루는 rewind(), 아직 처리하지 못한 영역을 앞으로 옮기는 compact(), 그리고 되돌릴 위치를 기록하고 그 위치로 돌아가는 mark() / reset() 이다. 이 절의 모든 예시에서는 capacity 가 10 인 버퍼를 사용한다.

아래 그림에서 v pos(n) 은 position, ^ lim(n) 은 limit, < cap(n) 은 capacity 를 가리키고, * 는 position 부터 limit 직전까지의 남은 영역을 나타낸다.

clear()

clear() 는 버퍼를 처음부터 다시 채울 준비로 만든다. 실제로 버퍼의 내용(바이트들)을 지우지는 않는다.[3][4]

  • position → 0

  • limit → capacity

  • mark → -1 (정의되지 않은 상태로 되돌아감)

allocate(10)
final var b = ByteBuffer.allocate(10);
// position=0, limit=10, capacity=10, mark=-1
             v pos(0)
     buffer: ********** < cap(10)
                       ^ lim(10)
limit(7).position(4).mark().position(6)
b.limit(7).position(4).mark().position(6);
// mark=4, position=6, limit=7, capacity=10
                   v pos(6)
     buffer: ------*--- < cap(10)
                    ^ lim(7)
b.clear()
b.clear();
assert b.position() == 0;
assert b.limit() == 10;
assert b.remaining() == 10;
// mark 는 정의되지 않은 상태이므로 reset() 호출 시 InvalidMarkException
             v pos(0)
     buffer: ********** < cap(10)
                       ^ lim(10)

rewind()

rewind() 는 이미 정해진 읽을(또는 기록할) 영역을 처음부터 다시 다루도록 되돌린다. limit 은 그대로 유지한다.[5][6]

  • position → 0

  • mark → -1

  • limit 유지

allocate(10).limit(7).position(4)
final var b = ByteBuffer.allocate(10).limit(7).position(4);
// position=4, limit=7, capacity=10, mark=-1
                 v pos(4)
     buffer: ----***--- < cap(10)
                    ^ lim(7)
b.rewind()
b.rewind();
assert b.position() == 0;
assert b.limit() == 7;                     // 변경되지 않음
assert b.remaining() == 7;
             v pos(0)
     buffer: *******--- < cap(10)
                    ^ lim(7)

compact()

compact() 는 아직 처리하지 못한 영역 (position ~ limit) 을 버퍼 앞쪽으로 옮긴 후, 그 뒤로 추가로 채울 준비를 한다.[7]

  • position ~ limit - 1 의 바이트들을 0 ~ (limit - position - 1) 로 복사한다.

  • position → limit - position (= 옮긴 바이트들의 바로 뒤)

  • limit → capacity

  • mark → -1

allocate(10)
final var b = ByteBuffer.allocate(10);
// position=0, limit=10, capacity=10, mark=-1
             v pos(0)
     buffer: ********** < cap(10)
                       ^ lim(10)
b.put(new byte[8])
b.put(new byte[8]);
// position=8, limit=10, capacity=10
                     v pos(8)
     buffer: --------** < cap(10)
                       ^ lim(10)
b.flip()
b.flip();
// position=0, limit=8, capacity=10
             v pos(0)
     buffer: ********-- < cap(10)
                     ^ lim(8)
b.position(3)
b.position(3);
// position=3, limit=8 (인덱스 3~7 의 5 바이트가 미처리 상태)
                v pos(3)
     buffer: ---*****-- < cap(10)
                     ^ lim(8)
b.compact()
b.compact();
assert b.position() == 5;                  // 미처리 5 바이트(인덱스 3~7)가 0~4 로 옮겨졌고, position 은 그 뒤
assert b.limit() == 10;
assert b.remaining() == 5;
                  v pos(5)
     buffer: -----***** < cap(10)
                       ^ lim(10)

전부 처리된 경우(position == limit)에는 옮길 바이트가 없으며, 결과적으로 clear() 와 같은 상태가 된다.

allocate(10).put(new byte[8]).flip()
final var b = ByteBuffer.allocate(10);
b.put(new byte[8]);                        // position=8, limit=10
b.flip();                                  // position=0, limit=8
             v pos(0)
     buffer: ********-- < cap(10)
                     ^ lim(8)
b.position(8)
b.position(8);
// position=8, limit=8 (0 바이트 미처리)
                     v pos(8)
     buffer: ---------- < cap(10)
                     ^ lim(8)
b.compact()
b.compact();
assert b.position() == 0;                  // == clear()
assert b.limit() == 10;
             v pos(0)
     buffer: ********** < cap(10)
                       ^ lim(10)

mark() / reset()

mark() 는 현재 position 을 되돌릴 위치로 기록해 두고, reset() 은 position 을 그 위치로 되돌린다.[8][9][10]

  • mark(). mark = position

  • reset(). position = mark. mark 가 정의되지 않은 상태(-1)에서 호출하면 InvalidMarkException 이 발생한다.

position 이나 limit 을 mark 보다 작은 값으로 설정하면 mark 는 다시 정의되지 않은 상태가 된다. 또한 clear(), flip(), rewind(), compact() 호출 시 mark 는 모두 -1 로 초기화된다.[11]

allocate(10)
final var b = ByteBuffer.allocate(10);
// position=0, limit=10, capacity=10, mark=-1
             v pos(0)
     buffer: ********** < cap(10)
                       ^ lim(10)
b.position(3).mark().position(7)
b.position(3).mark().position(7);
// mark=3, position=7, limit=10
                v mark(3) (1)
                    v pos(7)
     buffer: -------*** < cap(10)
                       ^ lim(10)
1 Buffer 는 position(), limit(), capacity() 와 달리 현재 설정된 mark 값을 그대로 반환하는 공개 메서드를 제공하지 않는다. mark 의 값은 reset() 을 호출한 직후 position() 의 값으로만 간접적으로 확인할 수 있다.
b.reset()
b.reset();
assert b.position() == 3;                  // mark 위치로 되돌아감
// mark=3, limit=10 은 그대로 유지
                v mark(3) (1)
                v pos(3)
     buffer: ---******* < cap(10)
                       ^ lim(10)
1 reset() 은 position = mark 만 수행할 뿐 mark 자체는 변경하지 않는다. 따라서 같은 지점으로 여러 번 되돌릴 수 있도록, mark 는 명시적으로 다시 설정하거나 폐기되기 전까지 그대로 유지된다.

java.nio.IntBuffer

byte 형이 아닌 int 형 단위로 값을 읽고 쓰는 버퍼이다. position, limit, capacity 등은 모두 int 요소의 개수로 세며, 한 번의 get()/put(int) 호출로 4 바이트(int 한 개)가 처리된다. 두 가지 방법으로 얻을 수 있다.[12]

java.nio.IntBuffer
package java.nio;

public abstract sealed class IntBuffer extends Buffer implements Comparable<IntBuffer> {

    ...
}

  • 새로 할당: IntBuffer.allocate(int capacity) 또는 IntBuffer.wrap(int[]). backing array 가 int[] 이다.

  • ByteBuffer 의 뷰(view): byteBuffer.asIntBuffer(). 별도의 메모리를 할당하지 않고 같은 바이트들을 int 단위로 보여주는 뷰(view)일 뿐이며, 원본 ByteBuffer 와 메모리를 공유한다. 따라서 한쪽의 변경이 다른 쪽에 반영된다. 단, position/limit/mark 는 독립적이다. 바이트 순서는 뷰 생성 시점의 원본 ByteBuffer.order() 를 따른다.

아래에 capacity 가 Integer.BYTES(4) 와 같은 ByteBuffer 를 할당한 후 0x7F_FF_FF_FF 값(= Integer.MAX_VALUE) 을 채워 넣었다.

final var bbuf = ByteBuffer.allocate(Integer.BYTES);
bbuf.put(0, new byte[] {(byte) 0x7F, (byte) 0xFF, (byte) 0xFF, (byte) 0xFF});

절대 위치를 명시했으므로 position 이 0 으로 유지되었다. bbuf 의 상태를 그림으로 나타내면 아래와 같다.

             v pos(0)
     buffer: **** < cap(4)
                 ^ lim(4)

이제 asIntBuffer() 메서드를 이용하여 뷰(view)를 하나 생성하자. 그 아래의 세 assert 구문은 asIntBuffer() 메서드에 명시된 내용 그대로이다.

final var ibuf = bbuf.asIntBuffer();
assert ibuf.position() == 0;
assert ibuf.capacity() == bbuf.remaining() / Integer.BYTES;
assert ibuf.limit() == bbuf.remaining() / Integer.BYTES;

ibuf 의 상태를 그림으로 나타내면 아래와 같다. capacity 는 1 이지만 각 요소의 크기는 Integer.BYTES(4 바이트)이므로, 실제로는 원본 bbuf 의 4 바이트 전체와 같은 영역을 가리킨다. 뷰는 backing array 를 드러내지 않으므로 ibuf.hasArray() 는 false 를 돌려준다.

             v pos(0)
     buffer: * < cap(1)
              ^ lim(1)

이제 ibuf 에서 얻은 int 형의 값은 0x7F_FF_FF_FF 과 같다.

final var i = ibuf.get();
assert i == Integer.MAX_VALUE;

java.nio.ByteOrder

다중 바이트로 구성되는 값(short, int, long, float, double, char)을 메모리에 어떻게 배열할 것인지를 바이트 순서(byte order, endianness)라고 한다. java.nio.ByteOrder 는 이 두 가지 순서를 표현하는 열거형이다.[13]

java.nio.ByteOrder
package java.nio;

public enum ByteOrder {

    LITTLE_ENDIAN,
    BIG_ENDIAN;

    public static ByteOrder nativeOrder() {...}
}

  • ByteOrder.BIG_ENDIAN. 최상위 바이트(MSB)가 가장 낮은 주소에 저장된다. 네트워크 바이트 순서와 같다.

  • ByteOrder.LITTLE_ENDIAN. 최하위 바이트(LSB)가 가장 낮은 주소에 저장된다. 대부분의 x86/x86_64, ARM 환경에서 네이티브로 사용한다.

  • ByteOrder.nativeOrder(). 현재 JVM 이 실행 중인 플랫폼의 네이티브 바이트 순서를 반환한다.

예를 들어 int 값 0x7F_FF_FF_FF 를 ByteBuffer 에 기록하면 바이트 순서에 따라 메모리 배열이 달라진다.

BIG_ENDIAN:    | 7F | FF | FF | FF |   <- 가장 낮은 주소가 MSB
LITTLE_ENDIAN: | FF | FF | FF | 7F |   <- 가장 낮은 주소가 LSB

새로 생성된 ByteBuffer 의 기본 바이트 순서는 항상 BIG_ENDIAN 이다. 플랫폼의 네이티브 순서로 바꾸려면 order(ByteOrder) 를 호출한다.

final var buf = ByteBuffer.allocate(Integer.BYTES);
assert buf.order() == ByteOrder.BIG_ENDIAN;         // 기본값
buf.order(ByteOrder.nativeOrder());                 // 네이티브 순서로 변경

바이트 순서는 getInt/putInt 등 다중 바이트 접근 메서드와 asIntBuffer() 등 뷰 생성 시 적용된다. 특히 뷰는 생성 시점의 바이트 순서를 그대로 쓰므로, 뷰를 만든 후 원본의 order() 를 바꾸어도 뷰의 바이트 순서는 변경되지 않는다.

예를 들어 java.nio.IntBuffer 절의 bbuf 에 0x7F, 0xFF, 0xFF, 0xFF 네 바이트를 기록한 상태에서, asIntBuffer() 호출 이전에 LITTLE_ENDIAN 으로 바꾸면 같은 바이트들이 다른 int 값으로 해석된다.

bbuf.order(ByteOrder.LITTLE_ENDIAN);     // 뷰 생성 전에 변경
final var ibuf = bbuf.asIntBuffer();
final var i = ibuf.get();
assert i == 0xFF_FF_FF_7F;               // 부호 있는 값으로는 -129

같은 메모리(7F FF FF FF)이지만 해석이 달라지는 것을 정리하면 아래와 같다.

바이트 순서 메모리 (낮은 인덱스 → 높은 인덱스) 해석된 int 값

BIG_ENDIAN

7F FF FF FF

0x7F_FF_FF_FF (= Integer.MAX_VALUE)

LITTLE_ENDIAN

7F FF FF FF

0xFF_FF_FF_7F (= -129)

네이티브 C 라이브러리나 x86 기반의 바이너리 프로토콜과 데이터를 주고받을 때에는 LSB 가 먼저 오는 octet sequence(예: 7F 00 00 00 으로 표현된 int 값 0x00_00_00_7F) 를 다루어야 하므로, LITTLE_ENDIAN 으로 명시적으로 바꿔서 사용하는 경우가 많다.
