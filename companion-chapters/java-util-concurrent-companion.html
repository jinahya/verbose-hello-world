java.util.concurrent.ExecutorService

java.util.concurrent.ExecutorService 는 Executor 위에 세 가지 기능을 더 추가한 확장 인터페이스이다. Java 19 부터는 AutoCloseable 까지 함께 구현해서 try-with-resources 안에서 자동 종료시킬 수도 있다.[1]

java.util.concurrent.ExecutorService
package java.util.concurrent;

public interface ExecutorService extends Executor, AutoCloseable {

    ...
}

ExecutorService 는 Executor 의 기능에 더해 결과 받기, 수명 관리, 묶어 제출의 세 가지 기능을 더 노출한다.

결과를 돌려받는 제출

단순히 "실행만 하는" execute(Runnable) 과 달리, 결과를 받을 수 있는 핸들(Future) 을 즉시 돌려주는 제출 메서드들이 있다.

  • <T> Future<T> submit(Callable<T>)

  • <T> Future<T> submit(Runnable, T)

  • Future<?> submit(Runnable)

수명 관리

풀의 종료를 명시적으로 다룰 수 있다. Executor 자체에는 "풀을 닫는다" 는 개념이 없다.

  • shutdown()

  • shutdownNow()

  • awaitTermination(…​)

  • isShutdown()

  • isTerminated()

  • close(). try-with-resources 종료 시 shutdown() 후 awaitTermination(…​) 까지 묶어 호출하는 기본 구현이 인터페이스에 들어 있다.

묶어 제출

여러 작업을 한 번에 제출하고, 모두 또는 어느 하나의 결과를 모아 받는다.

  • invokeAll(Collection<Callable>)

  • invokeAny(Collection<Callable>)

표준 라이브러리에는 이 인터페이스의 대표적 구현이 셋 있다. 고정 / 가변 크기 풀인 ThreadPoolExecutor, 지연·반복 스케줄링까지 처리하는 ScheduledThreadPoolExecutor, 그리고 작업(work) 훔치기(stealing) 풀 ForkJoinPool 이다.

Table 1. 표준 ExecutorService 구현
구현 성격

ThreadPoolExecutor

고정 / 가변 크기의 워커 풀과 작업 큐(BlockingQueue<Runnable>) 를 함께 다루는 가장 일반적인 풀.

ScheduledThreadPoolExecutor

ForkJoinPool

워커별 큐와 작업 훔치기(work-stealing) 스케줄링을 쓰는 풀. 이 부록의 java.util.concurrent.ForkJoinPool 절에서 따로 다룬다.

java.util.concurrent.Executors 팩토리는 이들에 대한 흔한 설정을 묶은 정적 메서드들(newFixedThreadPool, newCachedThreadPool, newSingleThreadExecutor, newScheduledThreadPool, newVirtualThreadPerTaskExecutor, …​) 을 제공한다. 마지막 newVirtualThreadPerTaskExecutor() 는 풀을 쓰지 않는다.

Executors.newVirtualThreadPerTaskExecutor()

Executors.newVirtualThreadPerTaskExecutor() 는 작업 한 건마다 새 가상 스레드를 만들어 실행하는 ExecutorService 를 돌려준다. 풀 크기를 조정하는 대신 작업마다 새 가상 스레드를 만든다는 점에서 위의 세 풀과 성격이 다르다. 가상 스레드가 블로킹 호출 위에서 캐리어 스레드를 자동으로 양보하므로, thread-per-task / thread-per-connection 모델을 수만 개의 동시 작업으로 확장할 수 있다.

그러나 호출자가 받는 타입은 여전히 ExecutorService 라서, Executor 를 매개변수로 받는 진입점에 그대로 넘길 수 있다.

java.util.concurrent.ForkJoinPool

책에서는 ForkJoinPool 을 공용 풀 (ForkJoinPool.commonPool()) 로만 쓴다. 공용 풀은 JVM 단위로 단 하나만 존재하는 정적 ForkJoinPool 인스턴스이며, 표준 라이브러리에서 executor 를 명시하지 않은 여러 비동기 진입점이 이 풀을 기본값으로 쓴다.

공용 풀이 기본값으로 등장하는 곳
CompletableFuture.runAsync(Runnable), CompletableFuture.supplyAsync(Supplier)

Executor 를 받지 않는 형태에서 기본 비동기 executor 로 쓰인다.

stage.thenXxxAsync(…​) (executor 미지정)

CompletionStage 의 Async 형태가 executor 를 받지 않으면 구현체가 정한 기본 비동기 실행기를 사용한다. CompletableFuture 는 기본적으로 공용 풀을 사용한다.

Collection.parallelStream(), Arrays.parallelSort(…​), …​

병렬 스트림과 병렬 정렬도 공용 풀 위에서 작업을 분할-정복한다.

공용 풀은 공유 자원이므로, 이 가운데 어느 곳에서 던진 작업이든 오래 블로킹하면 공용 풀을 함께 쓰는 다른 모든 사용자가 그 블로킹을 함께 짊어진다.

작업 훔치기 (work-stealing)

ForkJoinPool 은 ExecutorService 인터페이스를 구현하지만, 그 안에는 작업 훔치기 (work-stealing) 라는 고유한 스케줄링 알고리즘이 들어 있다. 공용 풀이 여러 API 의 기본값으로 쓰이는 이유도, 공용 풀에서 오래 블로킹하면 안 되는 이유도 이 알고리즘이 어떻게 동작하는지를 알면 더 분명해진다.

작업 훔치기의 핵심 아이디어는 단 하나이다. 모든 프로세서 코어를 가능한 한 비워두지 말 것. 이를 위해 풀은 일반적인 "단일 공유 큐 + 여러 워커" 모델 대신, 워커마다 자기만의 큐를 두고 비어 있는 워커가 바쁜 워커의 큐에서 작업을 훔쳐 와 실행한다.

작업 훔치기와 작업 공유

같은 "여러 워커가 작업을 나눠 처리" 라는 목표를 두고도, 두 가지 정반대의 접근이 가능하다.

  • 작업 공유 (work-sharing). 작업이 만들어지자마자 스케줄러가 즉시 어느 워커에게 줄지 결정한다. 모두가 바쁘다면 굳이 옮길 일이 없으므로 깔끔하지만, 결정의 부담이 생성 시점에 집중된다.

  • 작업 훔치기 (work-stealing). 작업은 일단 생성한 워커의 자기 큐에 쌓아 두고, 놀고 있는 워커가 필요할 때만 훔쳐 간다. "모두가 바쁘면 옮기지 않는다", 즉 워커 간 이동은 필요할 때만 일어난다.

후자는 부하가 균등할 때의 오버헤드를 거의 0 에 가깝게 만들고, 부하가 한쪽으로 몰릴 때만 작업을 옮긴다. 스케줄러가 끼어드는 일이 대부분의 시간 동안 거의 없다는 뜻이다.

Table 2. 작업 훔치기 알고리즘의 네 가지 핵심
요소 의미

워커별 큐 (local deque)

모든 워커가 공유하는 단일 큐 대신, 워커마다 별도의 양방향 큐 (deque) 를 둔다. 새 작업이 풀에 던져지면 던진 워커의 자기 큐에 쌓이며, 큐 단위의 경합이 자연스럽게 줄어든다.

자기 큐는 LIFO

워커는 자기 큐의 앞쪽에서 작업을 꺼낸다 (Last-In-First-Out). 방금 만들어 던진 서브태스크가 곧바로 다시 실행되므로 캐시 지역성이 보존된다.

훔치기는 FIFO

자기 큐가 비면, 임의의 다른 바쁜 워커를 골라 그 워커 큐의 뒤쪽에서 작업을 훔쳐 온다 (First-In-First-Out). 큐 앞쪽은 큐 주인이 사용하고 있으므로, 뒤쪽에서 훔치면 서로 부딪치지 않는다.

낮은 경합

위 두 규칙이 합쳐지면, 큐 주인과 훔치는 쪽이 서로 다른 끝을 사용하므로 락 경합이 최소화된다. 그래서 코어 수가 많아져도 선형에 가까운 확장성을 보인다.

이 알고리즘은 본래 분할-정복 (divide-and-conquer) 작업 (즉, 작업이 자기 자신을 서브태스크로 쪼개 (fork) 다시 풀에 던지고 결과를 모으는 (join) 패턴) 을 위해 설계되었다. 서브태스크가 부모 워커의 자기 큐에 쌓이고, 놀고 있는 다른 워커가 그것을 훔쳐가 병렬로 진행되며, 부모는 자기 큐의 다른 작업을 LIFO 로 계속 처리하는 과정이 자연스럽게 맞물려 돌아간다.

분할-정복 의사코드: 병렬 합산 (parallel sum)

배열의 합을 RecursiveTask 로 구해 보면, fork 와 join 두 호출이 어떻게 맞물려 동작하는지를 가장 단순한 코드로 볼 수 있다. 아래 코드는 설명을 위해 손으로 쓴 의사코드이며, 그대로 컴파일되지는 않는다 (THRESHOLD, sumInPlace 의 정의와 생성자, 접근 제어자 등을 생략했다).

다만 이 예제는 fork-join 의 동작을 보이기 위한 것일 뿐이다. 배열의 합 자체는 단순한 반복문으로 더하는 편이 빠르다. 합산은 원소마다 하는 일이 거의 없어 메모리 대역폭에 묶이는 작업이라, 태스크를 쪼개고 훔치는 비용이 병렬화로 얻는 이득을 넘어서기 때문이다.

class SumTask extends RecursiveTask<Long> {
    int[] a; int lo, hi;                    // 합할 구간 a[lo..hi)
    Long compute() {
        if (hi - lo <= THRESHOLD) {
            return sumInPlace(a, lo, hi);   // 작으면 직접 더한다
        }
        var mid = (lo + hi) >>> 1;
        var left  = new SumTask(a, lo, mid);
        var right = new SumTask(a, mid, hi);
        left.fork();                        // 왼쪽은 큐에 던지고
        var rs = right.compute();           // 오른쪽은 이 스레드에서 곧장 계산
        var ls = left.join();               // 왼쪽 결과를 회수 (또는 다른 워커가 끝낸 결과)
        return ls + rs;                     // 정복: 두 부분합을 더한다
    }
}

// 호출 측: 풀에 던지고 결과를 회수한다
var sum = ForkJoinPool.commonPool().invoke(new SumTask(a, 0, a.length));

left.fork() 가 자기 큐에 쌓아 둔 서브태스크는 같은 워커가 다른 일이 없을 때 LIFO 로 꺼내거나, 놀고 있는 다른 워커가 큐 뒤쪽에서 훔쳐 가 병렬로 처리한다. left.join() 시점에 그 결과가 이미 와 있으면 곧장 회수하고, 아직이면 그 시점에 기다리지 않고 다른 서브태스크를 도와 처리하다 결과를 받는다. 호출 측은 pool.invoke(task) 한 줄로 루트 태스크를 풀에 제출하고 최종 결과까지 받는다. 정복 단계가 ls + rs 한 줄로 끝나는 덕분에, 코드의 모든 줄이 분할-정복의 뼈대 자체를 보여 준다. 같은 뼈대가 병합 정렬, 트리 탐색, 행렬 곱 등 거의 모든 분할-정복 알고리즘에 그대로 들어맞으며, 결합 단계만 알고리즘에 맞게 바꿔 끼우면 된다.

Fork/Join Framework

ForkJoinPool / RecursiveTask / RecursiveAction 으로 작업 훔치기 알고리즘을 공개 API 로 처음 제공한 토대.

Virtual Threads

Java 21

가상 스레드의 기본 스케줄러가 작업 훔치기 ForkJoinPool 이다. 수백만 개의 가상 스레드를 훨씬 적은 수의 캐리어 (플랫폼) 스레드 위에서 분산시킨다.

직접 작업 훔치기 풀을 만들고 싶다면 Executors.newWorkStealingPool() 을 사용할 수 있다. 이 팩토리는 내부적으로 ForkJoinPool 을 만들어 ExecutorService 로 노출하며, 공용 풀과 별개의 인스턴스이므로 블로킹 작업을 격리하고 싶을 때 유용하다. "공용 풀이 공유 자원이라 부담스럽다" 는 우려에 대한 가장 직접적인 대처이기도 하다.

java.util.concurrent.CompletionStage<T>

CompletionStage<T> 의 메서드 이름은 두 축으로 갈린다. 다음 단계가 무엇을 할 것인가 (동사) 와 어디에서 할 것인가 (실행 위치) 가 그것이다. 책에서는 thenApply, thenAccept, thenCompose, exceptionally, whenComplete 다섯 동사의 기본 형태만 쓴다. 여기서는 나머지 동사와 실행 위치를 정하는 형태를 정리한다.

다른 동사

책에서 쓰지 않는 동사
thenRun (후속 동작)

  • 함수형 인자: Runnable

  • 다음 단계의 결과: Void. 이전 결과를 보지 않고 다음 동작만 실행한다.

thenCombine (두 단계 합성)

  • 함수형 인자: BiFunction<? super T, ? super U, ? extends V> (와 두 번째 CompletionStage<U>)

  • 다음 단계의 결과: V. 두 단계 모두 정상 완료된 뒤 결과를 모아 합성한다. 같은 방식으로 thenAcceptBoth, runAfterBoth 가 있다.

applyToEither, acceptEither, runAfterEither (둘 중 먼저)

  • 함수형 인자: 두 단계 중 하나가 정상 완료되면 실행되는 Function / Consumer / Runnable

  • 다음 단계의 결과: 정상 완료를 조건으로 결과를 변환 / 소비하거나 후속 동작을 실행한다. 두 단계가 모두 완료된 경우 어느 쪽 결과를 사용할지는 보장하지 않는다.

handle (예외 회복)

  • 함수형 인자: (결과, 예외) 쌍을 받는 BiFunction

  • 다음 단계의 결과: 정상 완료든 예외 완료든 함수가 돌려준 값으로 완료된다. 예외 완료를 정상 값으로 회복시킬 때 쓴다.

실행 위치

각 동사는 세 가지 형태로 오버로드되어 있다.

다음 단계의 실행 위치: 어디에서 할 것인가
thenXxx(…​)

실행 방식은 구현체가 정한다. CompletableFuture 에서는 단계를 완료한 스레드나 완료 처리를 수행하는 다른 스레드가 실행할 수 있고, 이미 완료된 단계라면 호출 스레드가 실행할 수도 있다.

thenXxxAsync(…​)

구현체가 정한 기본 비동기 executor 에서 실행한다.

thenXxxAsync(…​, Executor)

호출자가 지정한 Executor 에서 실행한다.

Async 접미사는 완료 호출의 비동기성이 아니라 후속 단계의 실행 위치를 결정한다. 즉 어떤 스레드가 다음 콜백을 실제로 실행하느냐가 이 세 가지로 갈린다.

java.util.concurrent.CompletableFuture<T>

팩토리 메서드

CompletableFuture 는 두 가지 시작점을 제공한다. 하나는 이미 완료된 단계를 즉시 만드는 시드(seed) 형 팩토리이고, 다른 하나는 작업을 비동기로 시작시키고 그 완료를 표현하는 단계를 돌려주는 디스패치 형 팩토리이다. 책에서는 디스패치 형의 runAsync(Runnable) 과 supplyAsync(Supplier<U>, Executor) 만 쓴다.

팩토리 메서드: 두 가지
시드(seed)

  • 메서드: completedFuture(value), failedFuture(throwable), completedStage(value), failedStage(throwable)

  • 돌려주는 단계의 상태: 이미 완료된 단계를 즉시 돌려준다. 시험에서 미리 결정된 값으로 잇기를 시작시키거나, 동기 값을 잇기 체인에 합류시킬 때 쓴다.

디스패치

  • 메서드: runAsync(Runnable), runAsync(Runnable, Executor), supplyAsync(Supplier<U>), supplyAsync(Supplier<U>, Executor)

  • 돌려주는 단계의 상태: 작업의 완료를 나타내는 단계를 돌려준다. 반환 시점에 이미 완료되어 있을 수도 있다. 받은 작업은 executor (또는 기본 비동기 executor) 에서 실행되며, 작업이 끝나면 단계가 그 결과로 완료된다.

여러 단계의 합성: allOf 와 anyOf

CompletionStage 의 인스턴스 메서드 thenCombine / applyToEither 가 두 단계의 합성을 다룬다면, CompletableFuture 는 가변 개수의 단계를 한 번에 묶는 정적 메서드를 추가로 제공한다.

allOf 가 돌려준 단계는 인자 중 어느 하나라도 예외 완료되면 그 예외로 함께 예외 완료된다. 즉 모두 정상 완료된 경우에만 정상 완료된다.

java.util.concurrent.SubmissionPublisher<T>

기다리지 않는 제출: offer

책에서는 SubmissionPublisher 에 항목을 넣을 때 submit(T) 만 쓴다. submit(T) 는 구독자의 버퍼가 가득 차면 공간이 생길 때까지 블로킹한다. 기다리지 않거나 정해진 시간까지만 기다리려면 offer 를 쓴다.[2]

  • offer(T item, BiPredicate<Subscriber<? super T>, ? super T> onDrop) 는 버퍼가 가득 찬 구독자가 있어도 기다리지 않는다.

  • offer(T item, long timeout, TimeUnit unit, BiPredicate<Subscriber<? super T>, ? super T> onDrop) 는 주어진 시간까지만 기다린다.

어느 쪽이든 항목을 넣지 못한 구독자에 대해 onDrop 핸들러가 불리고, 핸들러가 true 를 돌려주면 한 번 더 시도한다. false 를 돌려주거나 핸들러가 null 이면 그 구독자에게는 항목을 버린다.
