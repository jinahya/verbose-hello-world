== ReactiveHelloWorld

The reactive surface is *not a single interface*.
It comprises three package-private `org.reactivestreams.Publisher` classes (`Byte`/`Array`/
`String`), one public factory (`ReactiveHelloWorldPublishers`), one Flow adapter
(`HelloWorldFlow`), and a small lock-utility companion
(`ReactiveHelloWorldPublisherUtils`).

=== ReactiveHelloWorldBytePublisher

* *Spec compliance*: Rules 1.3, 1.7, 3.5, 3.6, 3.7, 3.9, 3.12 verified by raw-RS tests
(`ReactiveHelloWorld_Byte_PublisherTest`).
* *Lazy `byte[]` allocation*: source array is allocated inside the producer thread on the
first iteration with demand, so a `subscribe()` + `cancel()` without ever requesting
incurs no allocation cost.
* *Virtual-thread producer*: one virtual thread per `subscribe()` call.
Daemon (virtual threads always are); cannot block JVM shutdown.
* *Memory caveat*: an abandoned subscriber (subscribed but never requested + reference
dropped without `cancel`) parks the producer indefinitely on `Condition.await()`.
Virtual threads are GC-eligible only after the `Runnable` returns; while parked, the
closure captures (subscriber, lock, condition, demand, terminated) remain reachable.
This is an in-memory leak distinct from JVM-shutdown blocking and is *not currently
documented in the class Javadoc*.
* *One-byte-per-iteration emit loop*: each loop iteration decrements demand by 1 and
emits exactly one `onNext(Byte)`. Spec-compliant for any positive `n`.
* *Defensive check at the emit site*: previously guarded `onNext` with
`if (terminated.get()) break;` inside the lock.
Removed for educational clarity.
Trade-off: one stray `onNext` may slip past a concurrent `cancel()`, but this is
explicitly permitted by Rule 1.8 / 3.12 ("eventually").

=== ReactiveHelloWorldArrayPublisher

* *N:1 aggregation*: each unit of downstream demand spawns a fresh worker virtual thread
that subscribes to a new upstream `ReactiveHelloWorldBytePublisher`, accumulates the
12 bytes, and emits one `byte[]` downstream via `onNext`.
* *Open-ended stream*: does not naturally complete; only `cancel()`,
`request(n <= 0)`, or upstream error terminate it.
* *CountDownLatch sync*: each worker uses a `CountDownLatch(1)` to block its parent
producer until the upstream byte sequence completes.
* *Concurrent worker race*: when downstream demand arrives faster than upstream
completions, multiple workers race independently — order of `onNext(byte[])` emissions
is non-deterministic, but each array carries the same payload so observable behaviour
is invariant.
* *Same memory caveat as the Byte publisher* (parked producer + closure pinning).

=== ReactiveHelloWorldStringPublisher

* *1:1 Processor*: each `subscribe()` constructs a fresh single-use `HelloWorldStringEncoder`
{`Processor<byte[], String>`} that wraps the upstream byte-array publisher.
Demand is forwarded 1:1 — no prefetch, no buffering.
* *No producer thread*: signals run on whichever thread the upstream emits on.
* *Inner Subscription*: the encoder hands downstream a custom `Subscription` whose
`request(n)` is direct passthrough to upstream `request(n)`, except for `n <= 0` which
CASes `terminated` + sends `onError(IllegalArgumentException)` + cancels upstream.
* *Lifetime mirrors upstream*: when stacked on the open-ended array publisher, the string
publisher is open-ended too.
* `onNext(byte[])` site is the one remaining raw `lock.lock()/unlock()` block — uses
the helper `ReactiveHelloWorldPublisherUtils.lockAndGet(...)` returning a
`justTerminated` boolean.
The post-lock `if (justTerminated) upstreamSubscription.cancel();` co-locates fresh
termination with the cancel-propagation.

=== ReactiveHelloWorldPublishers (factory)

* Three public static methods: `ofBytes`, `ofArrays`, `ofStrings`.
* Each is a one-line composition: `new Array(new Byte(service))` etc.
* Return type `Publisher<byte[]>` (RS), not `Publisher<? extends byte[]>` — the latter
would be pointless since `byte[]` has no subtypes.
* Smoke-tested by `ReactiveHelloWorldPublishersTest` (three assertions: each factory
method returns non-`null` without throwing).

=== ReactiveHelloWorldPublisherUtils

* Three static helpers around `Lock`:
** `lockAndCall(Lock, Callable<V>) throws Exception` — value-producing, propagates
checked exceptions as-is.
** `lockAndGet(Lock, Supplier<T>)` — value-producing, wraps in `RuntimeException`.
** `lockAndRun(Lock, Runnable)` — side-effect only, wraps in `RuntimeException`.
* Used at signal sites for Rule 1.3 serialization (`onNext`/`onError`/`onComplete`)
and at the `signal()` helpers that need `condition.signalAll()` under the lock.
* *Not* used in producer-park loops or worker emit sites where the body has
checked-exception throws (`condition.await`) or multiple early-return paths — those
remain raw `lock.lock(); try { ... } finally { lock.unlock(); }` blocks.

=== HelloWorldFlow

* Type bridge only.
Three static methods `ofBytes`/`ofArrays`/`ofStrings` each wrap the corresponding
`ReactiveHelloWorldPublishers.ofXxx(service)` via
`org.reactivestreams.FlowAdapters.toFlowPublisher(...)`.
* No logic of its own.
Required because Mutiny 2.x+ and Helidon Common Reactive consume `Flow.Publisher`
directly.

=== Test coverage

The publisher trio is covered by *three axes* of tests:

[%unbreakable%autowidth.stretch,frame="none",grid="rows"]
|===
| Axis | Subject under test | Test driver | Files

| *Raw RS*
| Our publisher classes directly
| Hand-rolled `Subscriber` (via shared `LoggingFlowSubscriber` family)
| `ReactiveHelloWorld_(Byte\|Array\|String)_Publisher__Test`

| *Library composition* (Axis A)
| Our publisher as adapted through library X
| Each library's idiomatic subscriber / test framework
| `ReactiveHelloWorld_(Byte\|Array\|String)_Publisher_(Reactor\|RxJava3\|Mutiny\|Akka\|Helidon)_Test`

| *Library-native* (Axis B)
| Library X's own publisher factories
| Same as Axis A, but the publisher itself is created by library X (no use of our
publisher classes)
| `HelloWorld_Reactive_(Reactor\|RxJava3\|Mutiny\|Akka\|Helidon)_Test`
|===

* *Strict 1:1 demand-respect* (the `__randomLessThan12` scenario) is tested *only* at the
raw-RS level.
Library adapters (Mutiny, Reactor, RxJava3) prefetch upstream, breaking observable 1:1
demand forwarding; the scenario is dropped from Axis A by design.
* *Concurrent request/cancel* (`__cancel`) is tested at the raw-RS level and at the
library level for Reactor (via `BaseSubscriber`), RxJava3 (via `TestSubscriber`),
Mutiny (via `AssertSubscriber`), and Akka (via `TestSink.probe()`).
Helidon Axis-A `__cancel` is omitted (no test-subscriber in `helidon-common-reactive`
4.4.1).
* Total: ~90 tests across the matrix as of the latest revision.
