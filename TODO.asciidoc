== Deprecation

Candidates for `@Deprecated(forRemoval = true)`.

The criterion: every method should give out the `hello, world` bytes to a *target* that receives
them (a stream, a channel, a socket, a digest, a cipher, ...). A method is a candidate when it

* gives the bytes, one by one through a caller-supplied mapper, to a general-purpose container
  rather than to a byte sink; or
* duplicates another method with the same target (see <<Removed>>).

=== Already deprecated

[cols="2,3",options="header"]
|===
| Method | Reason

| `HelloWorld.accept(Consumer, Function)`
| A `Consumer` is not a byte sink; the method only iterates the bytes.

| `HelloWorld.accept(IntConsumer)`
| An `IntConsumer` is not a byte sink; the method only iterates the bytes.
|===

When removed, also remove the `_java_util_function` tests, and the then-empty `java.util.function`
section of `HelloWorld`.

=== Group A: general-purpose containers, per-byte mappers

Same reason as `accept`.

[cols="2,3",options="header"]
|===
| Method | Reason

| `HelloWorld.add(SequencedCollection, Function)`
| Adds each mapped byte to a collection; equivalent to `accept(collection::addLast, mapper)`.

| `HelloWorld.put(SequencedMap, Function, Function)`
| Puts a mapped key/value per byte; the map receives whatever the mappers produce, not
`hello, world`.

| `HelloWorld.all(Stream.Builder, Function)`
| Adds each mapped byte to a stream builder; same shape as `add(SequencedCollection, Function)`.
The name looks like a typo for `add`.

| `HelloWorld.add(IntStream.Builder)`
| Adds each byte, as an `int`, to an int stream builder.
|===

=== Removed

Removed outright, without deprecation, since nothing used them.

[cols="2,3",options="header"]
|===
| Method | Reason

| `AsynchronousHelloWorld.write_(AsynchronousByteChannel, A, CompletionHandler)`
| Duplicated `write(AsynchronousByteChannel, A, CompletionHandler)` with the same target; only built
on the stage-based `applyAsync(Function)` instead of the handler-based one. Unused and untested.

| `AsynchronousHelloWorld.write_(AsynchronousFileChannel, long, A, CompletionHandler)`
| Duplicated `write(AsynchronousFileChannel, long, A, CompletionHandler)` with the same target; only
built on the stage-based `applyAsync(Function)` instead of the handler-based one. Unused and
untested.
|===

=== Reviewed and kept

[cols="2,3",options="header"]
|===
| Method | Reason

| `HelloWorld.write(URLConnection)`, `HelloWorld.send(Socket)`, `HelloWorld.send(DatagramChannel, SocketAddress)`, `HelloWorld.send(DatagramChannel)`
| Delegate internally to `write(OutputStream)` / `send(DatagramSocket, ...)`, but each targets a
distinct JDK type.

| `HelloWorld.write(Writer)`
| A `Writer` is an `Appendable`, yet `Writer.write` is its own API.

| `HelloWorld.set(BitSet, int)`
| Borderline; a `BitSet` is a container, but it receives the bytes as they are, bit by bit, without
any mapper.

| `HelloWorld.setText(BreakIterator)`, `HelloWorld.method(HttpRequest.Builder, String)`,
`HelloWorld.update(...)`, `HelloWorld.setInput(Deflater)`
| Each is a genuine target receiving the bytes.

| `JdbcHelloWorld.*`
| Every method feeds a statement, a result set, a LOB, or an SQL output.
|===

== Runtime correctness (P1)

=== Asynchronous channel failures and append cleanup

* `01-verbose-hello-world-api/src/main/java/com/github/jinahya/hello/api/AsynchronousHelloWorld.java`:
  both handler-based `write(...)` loops call `channel.write(...)` without catching synchronous
  initiation failures. A standalone probe with `ExecutorHelloWorld` and a channel that throws
  `WritePendingException` leaves the stage-based `write(channel, attachment)` result incomplete;
  the exception escapes on the executor thread. Route initiation failures from the first and
  subsequent writes to `handler.failed(...)`, without catching exceptions thrown by the caller's
  own terminal callback and notifying it twice. Add deterministic regressions for both byte and
  file channels, including a failure after a partial write.
* In the same class, `append(Path, attachment, handler)` owns an open channel before invoking
  `write(...)`. If task submission is rejected synchronously, no completion callback closes it.
  Close owned channels on delegation/submission failure and preserve suppressed close failures;
  define whether rejection is thrown or delivered to the handler and test that contract.

=== Publisher cancellation and exceptional exits

* `HelloWorldStagePublisher.subscribe(...)`: downstream cancellation is observed only at the loop
  boundary. `stages.remove().join()` can wait forever on an unfinished stage, and that removed
  stage is absent from the deque cancelled in `finally`. A standalone probe confirms cancelling
  downstream leaves the current stage incomplete and uncancelled. Track the current stage and
  arrange for cancellation to release the waiting producer and cancel queued work. Test with an
  explicitly controlled, never-completing stage; verify producer termination as well as absence of
  downstream signals.
* `HelloWorldChunkPublisher.subscribe(...)`: the inner subscription is not retained, and
  `done.join()` cannot observe outer cancellation while upstream is stalled. Retain and cancel
  upstream, release the waiting producer when downstream cancels, and test with a stalled inner
  source. Also guard `upstream.subscribe(...)` and the producer loop: a synchronous throw currently
  escapes the virtual thread without closing the outer publisher or notifying its subscriber.

=== JDBC reader lifetime

* `JdbcHelloWorld.setCharacterStream(PreparedStatement, int)` closes its `StringReader` before
  returning. A driver that reads the bound reader during statement execution encounters a closed
  reader (a deferred-reader probe reports `Stream closed`). Keep it readable until the driver
  consumes it, consistently with `setNCharacterStream`
  and the LOB setters. Add a deferred-consumption regression that captures the bound reader and
  reads it after the helper returns; immediate Mockito answers and eager drivers miss this case.
  Review the adjacent ASCII/binary stream lifetime documentation at the same time.

=== Executable apps

* `appc`: the freshly built shaded jar fails with `NoSuchElementException` during Spring bean
  creation. The library registers `HelloWorldImpl` only in `module-info.java`; its jar has no
  `META-INF/services/com.github.jinahya.hello.api.HelloWorld`. `appb` supplies its own descriptor,
  so this is not a failure of every SPI app. Supply provider metadata for classpath consumers
  such as `appc` and `appd`, and verify discovery from the packaged artifacts.
* `appd`: the freshly built shaded jar fails with `WELD-001409: Ambiguous dependencies for type
  HelloWorld`. Its `META-INF/beans.xml` explicitly uses `bean-discovery-mode="all"`, discovering
  `HelloWorldImpl` alongside the `HelloWorldProvider` producer. Choose one CDI registration path,
  then verify producer-based SPI discovery after the ambiguity is removed. The assembled jar
  reproduces the ambiguity; the manual jar instead reaches the producer and fails with
  `NoSuchElementException`, so both discovery paths need coverage.

== API and documentation (P2)

* Document which `HelloWorld` methods remain exercises and what the packaged demos should print
  in that state. `set(byte[])` currently returns `null`, while `write(OutputStream)` and
  `write(WritableByteChannel)` omit the actual write. The current shaded `appa` and `appb` exit
  successfully but emit only a newline. A completed-example build, if desired, needs an explicit
  implementation path plus payload assertions.
* `HelloWorldArrayPublisher`, `HelloWorldBytePublisher`, and `HelloWorldStagePublisher` Javadoc
  incorrectly promises synchronous `onSubscribe` on the caller's thread. A queued-executor probe
  shows `HelloWorldBytePublisher.subscribe(...)` returns before `onSubscribe`; delivery is
  scheduled through `SubmissionPublisher`'s executor. Correct the threading and ordering claims
  and avoid tests or examples relying on synchronous subscription notification.
* `HelloWorld.send(DatagramChannel, SocketAddress)` Javadoc describes `SO_SNDBUF` checks,
  `Thread.onSpinWait()`, and related exceptions that are absent from the implementation. Reconcile
  the contract with the actual loop, and decide how a non-blocking channel repeatedly returning
  zero should yield or be bounded. Verify zero-progress behavior with a controlled channel.
* Decide whether `write(FileChannel, long)`, `setSeed(SecureRandom)`, `wrap(SSLEngine, ByteBuffer)`,
  and `write(SourceDataLine)` should use commented-out teaching bodies like the older targets.
* `HelloWorld` has an empty `java.util.jar` section; `JarOutputStream` is already covered by
  `write(OutputStream)` (see `HelloWorld_Java_Util_Jar__Test`). Remove the header or explicitly
  retain it as a placeholder.
* Add class-level Javadoc to `JdbcHelloWorldConstants` and `JdbcHelloWorldUtils`, and document
  `JdbcHelloWorldConstants.BYTES` and its relationship to `HelloWorld.BYTES`.
* `appc`'s `package-info.java` and `module-info.java` describe appending to a temporary file;
  `HelloWorldMain.print()` actually maps to a string and prints it. Align those descriptions.
* Consider a runnable example of asynchronous I/O (`write(AsynchronousByteChannel, ...)`,
  `append(Path, ...)`, or `sendAsync(...)`), handler-based `applyAsync`, and
  `StructuredConcurrencyHelloWorld`. The apps currently demonstrate only the stage-based mapper.
* Parameterize the raw `AsynchronousHelloWorld` and `ExecutorHelloWorld` types in `appc`'s
  `HelloWorldConfiguration`.
* `appd`: remove the obsolete `java:S6813` suppression for field injection (the app uses constructor
  injection), and fix the section comment from `Flow.Subscriber<byte>` to `Flow.Subscriber<byte[]>`.
* Expand `README.md` and the API README with the required JDK 27/preview setup, wrapper commands,
  exercise status, DI/CDI profile commands, and how to build/run the executable variants.
  The current API README contains only its title and one description line.
