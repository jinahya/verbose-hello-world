= 데드락
:toc:
:toclevels: 3

리액티브 스트림즈 구현에서 발견된 AB-BA 데드락에 관한 기록이다.
원인 분석부터 해결까지의 과정을 정리한다.

'''

== 1. 발견 경위

`mvn clean test` 를 `01-verbose-hello-world-api` 모듈 단위로 반복 실행하면서 *일관되지 않은* 실패 양상이 관찰되었다.

* 어떤 실행에서는 빌드가 정상 종료된다.
* 어떤 실행에서는 `HelloWorld_String_FlowPublisher_Helidon_Test.__random` 이 10초 타임아웃으로 실패한다.
* 또 다른 실행에서는 `HelloWorld_String_FlowPublisher_Mutiny_Test$Multi_Test.__random` 이 *끝나지 않고* 무한히 정지(hang)한다.

테스트 실행 순서는 surefire 의 기본 정책인 파일시스템 순서를 따르므로 결정적이지 않다.
이 때문에 어떤 테스트가 먼저 도는지에 따라 증상이 달라졌다.
처음에는 단순한 플레이키 테스트(flaky test)로 오인되었다.

[NOTE]
====
사용자 보고는 "가끔 통과, 가끔 실패, 가끔 영원히 끝나지 않음" 이었다.
이 보고가 디버깅의 출발점이었다.
====

'''

== 2. 진단

=== 2.1. 스레드 덤프

무한히 정지한 surefire JVM 에 대해 `jcmd <pid> Thread.dump_to_file -format=text dump.txt` 로 덤프를 떠 보았다.
핵심 두 스레드는 다음과 같다.

[%unbreakable]
[source]
----
Worker #155  BLOCKED  at AssertSubscriber.onItem
  (waiting to lock <AssertSubscriber@…>)
  ReactiveHelloWorldArrayPublisher.lambda$subscribe$1
    → lockAndRun(arrayLock) → subscriber.onNext(array)
    → StringEncoder.onNext
      → lockAndRun(stringLock) → downstream.onNext(string)
      → AssertSubscriber.onItem        ← 여기서 모니터 대기

Main         WAITING  at ReentrantLock.lock()
  (parking to wait for ArrayPublisher's lock)
  AssertSubscriber.request             ← synchronized, 모니터 소유
    → StringEncoder$1.request
    → upstreamSubscription.request
    → ArrayPublisher$1.signal
    → lockAndRun(arrayLock)            ← 여기서 락 대기
----

이 스택은 전형적인 *AB-BA* 데드락이다.

[%unbreakable%autowidth.stretch,frame="none",grid="rows"]
|===
| 스레드 | 보유 | 대기

| `Worker #155`
| `Array` 락 + `StringEncoder` 락
| `AssertSubscriber` 모니터

| `Main`
| `AssertSubscriber` 모니터
| `Array` 락
|===

두 스레드가 서로의 자원을 기다리고 있으므로 어느 쪽도 진행할 수 없다.

=== 2.2. 핵심 관찰

본질적인 두 가지 사실이 결합되어 사이클이 만들어진다.

. `AssertSubscriber.request(long)` 메서드와 `AssertSubscriber.onItem(T)` 메서드는 *같은 인스턴스 모니터* (`synchronized(this)`) 위에서 동기화된다.
. 우리 퍼블리셔의 워커 스레드는 *자기 락(`ReentrantLock`)을 잡은 채로* `subscriber.onNext(...)` 를 호출한다.

이 두 조건이 결합되면, 한쪽 스레드가 모니터를 잡고 락을 기다리고 반대쪽 스레드가 락을 잡고 모니터를 기다리는 *사이클* 이 형성된다.

=== 2.3. 왜 라이브러리마다 다른가?

데드락이 *Mutiny* 와 *Helidon* 테스트에서만 관찰되고 *Reactor* / *RxJava3* / *Akka* 에서는 관찰되지 않은 이유는, 각 라이브러리의 기본 구독자가 어떻게 동기화하는지에 달려 있다.

[%unbreakable%autowidth.stretch,frame="none",grid="rows"]
|===
| 라이브러리 | 구독자 클래스 | `request` / `onNext` 동기화 | 데드락

| Mutiny
| `AssertSubscriber`
| `synchronized(this)` (양쪽 모두)
| 발생 (정지)

| Helidon
| `Multi.collectList()` 내부 경로
| 큰 demand(`Long.MAX_VALUE`) 요청 후 자체 락 사용
| 발생 (10초 타임아웃)

| Reactor
| `BaseSubscriber`
| 동기화 없음
| 발생하지 않음

| RxJava3
| `TestSubscriber`
| 동기화 없음
| 발생하지 않음

| Akka
| `TestSink.probe()`
| 액터 메일박스 기반 (모니터 미사용)
| 발생하지 않음
|===

Reactor 와 RxJava3 가 데드락을 *우연히* 피한 것은 그들의 구독자가 `synchronized` 를 쓰지 않기 때문이다.
이것은 라이브러리의 구현 선택일 뿐 Reactive Streams 1.0 스펙이 강제하는 부분은 아니다.
즉, 우리 퍼블리셔의 버그는 *모든* 동기화하는 구독자에 대해 항상 데드락을 일으킬 수 있는 *잠재적 결함* 이었다.

'''

== 3. 원인

세 퍼블리셔 모두 동일한 안티패턴을 가지고 있었다.

[%unbreakable]
[source,java]
----
lockAndRun(lock, () -> {
    subscriber.onNext(item);   // ← 락을 보유한 채 사용자 코드 호출
});
----

이 패턴은 두 가지 문제를 동시에 야기한다.

. *시그널 직렬화(Rule 1.3)* 는 만족하지만, *사용자 코드 실행 중에도 락을 계속 보유* 한다.
. 사용자 코드 안에서 `Subscription#request(long)` 를 재귀적으로 호출하는 시나리오(Rule 3.2 에서 명시적으로 허용)에서, 다른 스레드가 같은 락을 기다리게 되어 사이클이 형성된다.

리액티브 스트림즈 생태계에서는 다음이 사실상 표준이다.

[quote]
____
A `Publisher` MUST NOT hold any internal lock while invoking subscriber signal methods.

`Publisher` 는 구독자 시그널 메서드를 호출하는 동안 어떠한 내부 락도 보유해서는 안 된다.
____

이 규칙은 스펙의 명시 조항은 아니지만, TCK 의 Rule 3.2 (재귀 `request`) 검증이 실질적으로 강제한다.
RxJava, Reactor, Mutiny, SmallRye 의 자체 구현체는 모두 *CAS-WIP drain* 패턴으로 이를 회피한다.

[NOTE]
====
이것은 *우리* 퍼블리셔의 버그이지 Mutiny 의 버그가 아니다.
Mutiny 의 `AssertSubscriber` 가 `request` / `onItem` 을 `synchronized(this)` 로 묶는 것은 Rule 2.7 (구독자의 `request`/`cancel` 호출은 직렬화되어야 한다)을 만족하기 위한 정당한 구현이다.
JDK 도 결백하다.
가상 스레드와 `ReentrantLock` 은 모두 올바르게 동작하고 있으며, 다만 우리 코드가 만든 *논리적* 사이클을 막아 줄 수는 없다.
====

'''

== 4. 해결의 세 가지 원칙

세 퍼블리셔에 공통적으로 적용한 원칙이다.

=== 4.1. 시그널은 락 *바깥* 에서만 호출한다

`subscriber.onNext` / `onError` / `onComplete` 의 호출 사이트에서 `lockAndRun(...)` 래퍼를 제거한다.
이것이 데드락 사이클을 끊는 핵심이다.

=== 4.2. 시그널 직렬화는 *단일 송신 스레드* 로 보장한다

락을 제거하면 여러 스레드가 동시에 `onNext` 를 호출할 위험이 생긴다(Rule 1.3 위반).
이를 막기 위해 시그널을 보낼 *하나의 송신 스레드* 만 두기로 한다.

[%unbreakable%autowidth.stretch,frame="none",grid="rows"]
|===
| 퍼블리셔 | 단일 송신자

| `ReactiveHelloWorldBytePublisher`
| 프로듀서 가상 스레드 (애초에 단일)

| `ReactiveHelloWorldArrayPublisher`
| 외부 프로듀서 스레드 (워커-당-수요 분기 폐기, *순차화*)

| `ReactiveHelloWorldStringPublisher` (StringEncoder)
| 업스트림(이제는 단일 스레드)이 호출하는 그대로
|===

=== 4.3. `request(n ≤ 0)` 의 `onError` 도 프로듀서에 위임한다

`request(n ≤ 0)` 는 호출자 스레드에서 직접 `onError` 를 보내지 않는다.
다음 두 가지만 한다.

. `AtomicReference<Throwable> pendingError` 에 예외를 적재한다.
. `terminated` 를 CAS 로 `true` 로 바꾸고, 프로듀서를 `signalAll()` 로 깨운 뒤 즉시 반환한다.

이렇게 하면 프로듀서가 다음 루프 반복에서 `terminated` 와 `pendingError` 를 확인하여 *락 바깥* 에서 `onError` 를 전달한다.
호출자 스레드는 락을 보유한 채 사용자 코드를 실행할 필요가 전혀 없다.

이 패턴의 코드 골격은 다음과 같다.

[%unbreakable]
[source,java]
----
final var pendingError = new AtomicReference<Throwable>();

// 구독의 request:
@Override
public void request(final long n) {
    if (terminated.get()) {
        return;
    }
    if (n <= 0L) {
        pendingError.compareAndSet(null, new IllegalArgumentException(
                "n(" + n + ") is not positive"));
        if (terminated.compareAndSet(false, true)) {
            lockAndRun(lock, condition::signalAll);   // 프로듀서 깨우기
        }
        return;
    }
    demand.accumulateAndGet(n, ...);
    signal();
}

// 프로듀서 루프:
while (true) {
    lock.lock();
    try {
        while (demand.get() == 0L && !terminated.get()) {
            condition.await();
        }
    } finally {
        lock.unlock();
    }
    if (terminated.get()) {
        final var err = pendingError.get();
        if (err != null) {
            try { s.onError(err); } catch (final Throwable st) { /* 무시 */ }
        }
        return;
    }
    // ... 정상 emission (락 바깥) ...
}
----

핵심은 `s.onError(err)` 호출이 `lock.unlock()` *이후* 에 일어난다는 점이다.

'''

== 5. 퍼블리셔별 적용

=== 5.1. `ReactiveHelloWorldBytePublisher`

* 프로듀서가 본래 단일 송신자이므로 구조 변경은 최소이다.
* `onNext` / `onComplete` 를 둘러싸던 `lockAndRun(...)` 블록을 모두 제거하였다.
* `pendingError` 패턴 도입.
* `service.set(byte[])` 호출 실패 시의 `onError` 도 락 바깥에서 호출하도록 정리하였다.

=== 5.2. `ReactiveHelloWorldArrayPublisher`

* 이전 모델은 *demand 단위마다* `Thread.ofVirtual().start(...)` 로 워커를 분기하여 여러 워커가 병렬로 `onNext` 를 보냈다.
이 모델은 락이 있어야만 직렬화가 보장되는 구조였다.
* *순차화* 로 변경하였다.
외부 프로듀서 스레드가 직접 업스트림 `ReactiveHelloWorldBytePublisher` 를 구독하고, 12바이트를 누적할 때까지 `CountDownLatch` 로 기다린 뒤, 락 없이 다운스트림에 `onNext(array)` 를 호출한다.
* 부수 효과로 `Long.MAX_VALUE` 만큼의 demand 가 들어와도 워커 수백만 개를 분기하지 않게 되었다.
이전 실행에서 관찰되던 "가상 스레드 1.4M 개" 폭주도 함께 해소되었다.

=== 5.3. `ReactiveHelloWorldStringPublisher` (`StringEncoder`)

* 업스트림이 이제 단일 스레드(`ArrayPublisher` 의 프로듀서)이므로, 업스트림 시그널 사이의 직렬화는 *자동으로* 보장된다.
* 내부 `ReentrantLock` 을 *완전히 제거* 하였다.
* 종료 여부는 `AtomicBoolean terminated` 의 CAS 만으로 가드한다.
* `request(n ≤ 0)` 는 CAS 가 성공하면 *직접* `downstream.onError(...)` 를 호출한다.
업스트림이 단일 스레드이고 종료 시그널이 한 번만 발생하도록 CAS 가 보장하므로, Rule 1.3 / 1.7 위반이 발생하지 않는다.

'''

== 6. 검증

=== 6.1. 결정적 재현 테스트

문제의 사이클을 1초 안에 재현하는 단위 테스트를 추가하였다.
파일은 `ReactiveHelloWorldPublisher__Deadlock_Test` 이며, 세 시나리오(`bytePublisher`, `arrayPublisher`, `stringPublisher`) 각각에서 다음 단계를 수행한다.

. 동기화하는 구독자(`Subscriber<T>` with `synchronized onNext`)를 만들어 퍼블리셔에 구독한다.
. 메인 스레드가 구독자 모니터를 잡은 채(`synchronized (subscriber) { ... }`) `request(1)` 을 보낸다.
. 200ms 대기.
워커가 `lockAndRun(lock, () -> subscriber.onNext(...))` 까지 진입했다고 가정한다.
. 별도 데몬 스레드에서 `request(1)` 을 다시 보낸다.
이 호출 안의 `signal()` 이 락을 잡으려고 시도한다.
. `join(1s)` 이후 데몬이 살아 있으면 데드락으로 판정한다.

이 테스트는 *수정 전* 에는 Array/String 시나리오에서 1초 후 어서션 실패로 데드락을 확인시켜 주고, *수정 후* 에는 셋 다 1초 이내에 통과한다.

=== 6.2. 풀 스위트 실행

`mvn clean test -pl 01-verbose-hello-world-api` 를 *3회 연속* 실행하여 결과를 확인하였다.

[%unbreakable%autowidth.stretch,frame="none",grid="rows"]
|===
| 실행 | 수정 전 | 수정 후

| 1회차
| Helidon `__random` 타임아웃 실패
| 통과 (839 tests)

| 2회차
| Helidon `__random` 타임아웃 실패
| 통과 (842 tests, 무관한 BitSet 플레이키 1건)

| 3회차
| Mutiny `__random` 무한 정지
| 통과 (837 tests)
|===

수정 후 3회 연속 Reactive 계열에서는 어떠한 데드락이나 타임아웃도 발생하지 않았다.
2회차의 실패 1건은 `HelloWorld_Set_BitSet_Index_Test` 의 무관한 플레이키 이슈로, 본 데드락과 관련이 없다.

'''

== 7. 교훈

. *퍼블리셔 안에서 사용자 코드를 호출할 때는 어떠한 내부 락도 보유해서는 안 된다.*
Reactive Streams 스펙의 명시 규칙은 아니지만, TCK 의 Rule 3.2 (재귀 `request`) 검증이 실질적으로 강제한다.
RxJava, Reactor, Mutiny 등 모든 주류 구현체가 이 규칙을 따른다.

. *시그널 직렬화는 락이 아니라 단일 송신 스레드 또는 CAS-WIP drain 으로 달성한다.*
락은 가장 자연스러운 도구처럼 보이지만, 사용자 코드와 락이 결합하면 데드락이 거의 필연적으로 발생한다.

. *TCK 통과는 충분조건이 아니다.*
우리 퍼블리셔는 raw RS 레벨에서 모든 시나리오를 통과했지만, 동기화하는 구독자(Mutiny `AssertSubscriber`, Vert.x `ReactiveReadStream` 등)와 만나는 *실제* 통합 환경에서는 데드락이 났다.
TCK 가 검증하지 못하는 *교차* 시나리오가 존재한다.

. *플레이키 테스트의 원인은 종종 동기화 결함이다.*
"가끔 통과, 가끔 실패" 라는 증상은 단순한 시간 의존성보다 *경합 조건* 일 가능성이 높다.
정지한 JVM 에 대해 스레드 덤프를 떠 보는 것이 가장 빠른 진단법이다.

'''
