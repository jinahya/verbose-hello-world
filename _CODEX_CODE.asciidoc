== Root

=== `pom.xml`

Severity: high

Surefire is configured with `<argLine>--enable-preview</argLine>` only (`lines 697-704`). The comments directly above it show Mockito Java-agent candidates, but both are commented out.

Impact: `./mvnw test` fails in the API module on JDK 25 because Mockito inline mocking tries to self-attach Byte Buddy at runtime.

Observed:

[source,text]
----
Tests run: 944, Failures: 0, Errors: 614, Skipped: 117
Could not initialize inline Byte Buddy mock maker.
It appears as if your JDK does not supply a working agent attachment mechanism.
Java               : 25
JVM vendor name    : Eclipse Adoptium
JVM vendor version : 25.0.3+9-LTS
----

This stops the reactor before later modules are tested.

Fix direction: configure Surefire to preserve JaCoCo's late-evaluated `@{argLine}`, keep `--enable-preview`, and pass Mockito as a startup Java agent instead of relying on runtime self-attachment.

Severity: medium

`main()` uses `ServiceLoader.load(HelloWorld.class).iterator().next()` without checking whether a provider exists (`lines 56-60`).

== `03-verbose-hello-world-app/03-verbose-hello-world-appc`

=== `03-verbose-hello-world-app/03-verbose-hello-world-appc/pom.xml`

Severity: medium

The module declares `verbose-hello-world-lib` as a runtime dependency (`lines 27-31`), while the Spring configuration obtains `HelloWorld` through `ServiceLoader`. In the shaded classpath artifact, `HelloWorldImpl.class` is present but `META-INF/services/com.github.jinahya.hello.api.HelloWorld` is not.

Impact: packaging succeeds, but the Spring app cannot create its context from the shaded jar.

== `03-verbose-hello-world-app/04-verbose-hello-world-appd`

=== `03-verbose-hello-world-app/04-verbose-hello-world-appd/src/main/resources/META-INF/beans.xml`

Severity: medium

The CDI descriptor uses `bean-discovery-mode="all"` (`line 23`). In the shaded app, that makes `HelloWorldImpl` discoverable as a managed bean while `HelloWorldProvider` also declares a default-qualified producer for `HelloWorld`.

Impact: Weld sees two default `HelloWorld` candidates and aborts deployment.

=== `03-verbose-hello-world-app/04-verbose-hello-world-appd/src/main/java/com/github/jinahya/hello/appd/HelloWorldMain.java`

Severity: medium

The constructor injects an unqualified `HelloWorld` (`lines 71-74`). At runtime there are two default-qualified candidates: the managed `HelloWorldImpl` and the producer method in `HelloWorldProvider`.

Observed:

[source,text]
----
WELD-001409: Ambiguous dependencies for type HelloWorld with qualifiers @Default
Possible dependencies:
- Producer Method [HelloWorld] with qualifiers [@Any @Default]
- Managed Bean [class com.github.jinahya.hello.lib.HelloWorldImpl] with qualifiers [@Any @Default]
----

=== `03-verbose-hello-world-app/04-verbose-hello-world-appd/src/main/java/com/github/jinahya/hello/appd/HelloWorldProvider.java`

Severity: medium

`produce()` creates a default-qualified `HelloWorld` producer by calling `ServiceLoader.load(HelloWorld.class).iterator().next()` (`lines 45-47`).

Impact: together with Weld's managed discovery of `HelloWorldImpl`, this creates the ambiguous dependency that prevents `appd` from starting. The current shaded `appd` jar also lacks `META-INF/services/com.github.jinahya.hello.api.HelloWorld`, so this producer would be fragile even after the ambiguity is removed.

Fix direction: remove the producer and inject the managed `HelloWorldImpl`, qualify the produced bean and injection point, mark one candidate as an alternative, or restrict bean discovery to the intended source.
